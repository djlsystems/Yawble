# Yawble core: contributor rules

For people and coding agents working on this repository. Rules that are load-bearing, and the failure each one prevents. Most name the test that pins them; keep that test green and keep the rule true when you change the code. For what the product is and how to build it, see `README.md` and `docs/architecture.md`.

The Host runs in a Linux container. An agent child starts in its own session (`setsid`), and its process group is killed when the run ends, so a detached grandchild does not outlive it. A command is resolved with `PathSearch.Find`, and a miss is a launch failure once the launch has looked again for about 30 seconds. The launch lives in `ChildProcess`, which agent and plugin members share. Pinned by `ChildProcessTests`, `ProcessAgentRunnerLaunchTests.The_child_leads_its_own_process_group`, `ProcessAgentRunnerLaunchTests.A_detached_grandchild_does_not_outlive_the_run`, `ProcessAgentRunnerLaunchTests.A_command_not_on_PATH_is_a_launch_failure` and `PathSearchTests.A_missing_command_is_null`.

A program missing at launch is not an agent fault. The shared install every member launches from is replaced in place while a CLI updates, so a launch can find no program for a few seconds. `ChildProcess.FindAsync` looks again every few seconds for about 30 (`LaunchLookup`, injectable so tests do not wait), and a program that appears is launched as normal with nothing recorded but one progress line. One that never appears fails with the class `launch-missing`, whose words say the program was not found when the run started, may be being installed or updated, and that re-sending the instruction will try again; they ask nobody to repair anything. The Manager prompt and skill say such a failure is re-sent, and escalated to a person only when it has already happened twice. Pinned by `LaunchMissingTests.A_program_missing_at_launch_that_appears_two_seconds_later_starts_the_run_normally`, `LaunchMissingTests.A_program_that_never_appears_fails_launch_missing_and_is_not_an_agent_fault` and `LaunchMissingTests.The_Managers_context_for_a_launch_missing_failure_says_re_send_and_names_nobody_to_repair_anything`.

An agent CLI updates only when the platform says so. The install is shared, so every launch the Host makes of a built-in self-updating CLI (a member, the Concierge's terminal, the sign-in probe, the tool pre-flight's listing) carries its preset's `updates` declaration, which turns the CLI's own updater off. That is a variable set after the preset's and team's env, or for codex a `-c` argument placed after the launch's own. The one exception is codex's pre-flight listing (`mcp list`, `features list`, `debug prompt-input`), which carries only the environment: codex's key is a launch argument those listing subcommands never act on, and they neither check for nor download an update. Updates happen at the container's start (`ensure-agent-clis.sh`, before the Host; a `control` container installs no CLI and logs one line saying so) and when a person asks (`POST /api/agents/{name}/update`). An update goes through control's one `AgentUpdateGate`, across every worker: it waits for that command's runs in flight on any worker, and new launches of it on any worker wait for the update. They are held, never failed. In `control` a run takes its share of the gate before it is sent to a worker and keeps it until it ends, however it ends (a run on a dropped worker keeps it until it ends or is lost); in `all` the Host's own worker takes it, so a run counts once. Once the gate has drained the update runs once, on the connected worker with the most headroom at that moment; with none connected it fails saying nothing was run, and a worker lost while it updates fails it saying whether the install changed is not known. A member's launch carries both this and its preset's isolation, neither replacing the other. Pinned by `AgentUpdatesTests.Every_launch_of_a_self_updating_preset_carries_its_update_off`, `AgentUpdatesTests.The_Concierges_terminal_carries_the_update_off`, `AgentUpdatesTests.A_members_launch_sets_the_update_off_last_so_no_preset_or_team_env_turns_it_back_on`, `AgentUpdatesTests.A_members_launch_carries_its_isolation_and_its_update_off`, `AgentUpdatesTests.A_members_process_gets_the_isolation_and_the_update_off_variables_together`, `AgentToolPreflightTests.A_member_is_listed_with_its_isolation_and_the_concierge_without_it` `AgentUpdatesTests.A_platform_update_waits_for_the_run_in_flight_holds_a_new_launch_and_that_launch_then_starts`, `ControlUpdateGateTests` (`In_control_a_run_holds_a_share_of_its_command_until_it_ends_however_it_ends`, `The_update_runs_on_one_worker_after_every_share_is_released`, `The_update_runs_on_the_worker_with_most_headroom_when_it_starts_not_when_asked`, `No_worker_when_it_is_time_fails_the_update_and_lets_launches_go`, `A_worker_lost_while_updating_fails_it_and_lets_launches_go`, `A_run_on_a_dropped_worker_keeps_its_share_until_it_is_lost_or_ends`, `In_all_a_run_is_counted_once`) and `AgentCliOnWorkerProcessTests.An_update_waits_for_runs_on_two_workers_holds_launches_on_both_and_runs_once`.

The Agents screen shows each built-in preset's CLI version, when it last changed and who brought it (a container start, or a person named by email), read from the Host's CLI version record (`cli-versions.jsonl`), the one `yawble doctor` and `yawble agents` read. Nothing is estimated: a version the record lacks reads "version not known", and a record that never saw the version change says how far back it looked instead of an update time. `GET /api/agents` gives it to a person as `cliVersions` (a machine principal gets none), and a finished update's `result` carries the entry as `cliVersion` after writing its own line, which the row shows in place, saying so when the version did not change. A version that is not known has no `updatedAt` or `updatedBy` either: the line where it went missing is not an update. The row's outcome says only what was measured - a failed command names its exit code and still compares the versions before and after (it can have moved them), and a preset that declares no update command says nothing was run. The update button stays `HumansOnly` and goes through `AgentUpdateGate`. Pinned by `AgentCliVersionRouteTests.A_person_reads_each_presets_version_when_it_changed_and_who_brought_it`, `AgentCliVersionRouteTests.The_update_route_answers_with_the_entry_after_its_own_line_and_records_the_person`, `AgentCliVersionRouteTests.A_version_that_is_not_known_has_no_update_time_and_no_one_who_brought_it` and the web mount tests in `agents-dialog-versions.mount.spec.ts`.

A person's update is asked for, never awaited. `POST /api/agents/{name}/update` answers 202 at once with the state `AgentUpdateGate` holds (`AgentUpdateGate.Request`), and `GET` on the same path reads it back, so no request stays open for minutes and closing the dialog or reloading cancels nothing: reopening reads the same state. The state is the gate's, never estimated: `waiting` with `running` and `inFlight` naming the team and member of each run it waits for (as `/api/wip` names a slot's holder) and `held` naming each launch it holds, `updating` from the moment the last of those runs leaves (drawn under the gate's lock, so it never reads "waiting for 0 runs"), then the last one's outcome - `done` with its measured `result`, `cancelled`, or `failed` with its sentence - kept until the Host restarts. The row reads "Waiting for N <command> runs to finish: team / member, ...", "Updating…", then the outcome, polling while the update is in the gate. `DELETE` cancels an update only while it waits: it is removed, nothing runs, and the launches it held go ahead at once (`agent.update-cancelled`); a running update answers 409 with a sentence. One update per command at a time: asked again, the route answers the one in the gate. A launch held behind an update is held, never failed: it says "Waiting for the <command> update" once as its progress, and its kanban card carries "waiting for the <command> update" from `GET /api/agents/updates`. The update route, its read, its cancel and that list are all `HumansOnly`. Pinned by `AgentUpdatesTests.A_persons_update_asked_while_a_run_is_in_flight_answers_at_once_names_that_run_then_updates_then_says_its_outcome`, `AgentUpdatesTests.Cancelling_a_waiting_update_removes_it_and_releases_the_launches_it_held`, `AgentCliVersionRouteTests.An_update_asked_while_a_run_is_in_flight_answers_at_once_waiting_on_that_run_and_reads_the_same_when_the_dialog_reopens`, `AgentCliVersionRouteTests.A_running_update_cannot_be_cancelled` and the web mount tests in `agents-dialog-update-waiting.mount.spec.ts`.

## Identity

- The code says **Harness**. The product name is **Yawble** and, in code, it appears in exactly two files: `web/src/presentation/product.ts` and the `productName` in `web/package.json`, so renaming the product edits those and nothing that carries identifiers. Pinned by `BrandLeakTests.Brand_strings_stay_out_of_the_code` and `BrandLeakTests.The_brand_lives_in_the_presentation_layer`. The GitHub repository is `djlsystems/Yawble`. The one exception is `cli/`, the operator CLI: its binary is `yawble`, so the brand is its name, and `BrandLeakTests` skips `cli/` by path. The CLI shares this repository's tag, GitHub Release and version number (`v<yyyy.mm.dd.N>`, cut by `scripts/release.ps1` for image and binary together); there is no separate CLI repository. Not pinned: one tag for both is the release script's arithmetic, which `scripts/tests/release-functions.tests.ps1` checks offline, not a behaviour either suite runs.
- Environment variables use the `HARNESS_` prefix. A catalog or team env entry that sets one is dropped, not overwritten: a hand-edited file must not be able to hand a member another principal's credential. Pinned by `AgentEnvironmentTests.Harness_entries_in_a_catalog_or_team_env_are_dropped`.
- A headless child receives only its own command's credential variables - its `credentialVariable` in `auth-probes.json` and every variable its preset's `issuedCredential` declares - plus `GH_TOKEN` when its team has a GitHub remote, whatever the preset's credential source. Every other provider key, `GITHUB_TOKEN`, and every variable another command's `issuedCredential` declares (its kinds' variables and what it displaces) are REMOVED at the spawn site (`AgentEnvironment.ApplyCredential` with the other commands' names from `RunCredentials.ResolveAsync`, then `AgentEnvironment.ScopeProviderKeys`), not set empty; a key handed in explicitly (a catalog entry's own env, a team env entry) is kept, and no declaration displaces `GH_TOKEN`. Pinned by `AgentEnvironmentTests.A_child_receives_only_its_own_provider_key`, `AgentEnvironmentTests.A_team_with_a_GitHub_remote_hands_its_member_GH_TOKEN_and_no_other_foreign_key`, `AgentEnvironmentTests.Copilot_keeps_GH_TOKEN_and_loses_every_other_provider_key`, `HomeCredentialLaunchTests.A_home_run_of_each_built_in_headless_preset_receives_no_other_commands_declared_variable_and_keeps_its_own`, `HomeCredentialLaunchTests.A_team_env_or_catalog_entry_naming_another_commands_variable_is_kept_on_home` and `IssuedCredentialLaunchTests.Every_other_providers_key_is_still_scoped_away_under_issued`. The Host's own git follows the same rule: `GH_TOKEN` only for an operation on a GitHub team's remote, and a remote given by NAME (`ls-remote origin`, the `repo` refresh) is judged by the team's remotes, not by its spelling, or GitHub refuses the check while Fetch works. Pinned by `LsRemoteTokenTests`. **Not true for the Concierge:** its PTY path merges into the Host's environment and cannot remove a variable (see `AgentEnvironment.MustBeAbsent`), so it still inherits every provider key. **The Concierge also keeps every tool** (B001K): it is the person's own session, so it launches with the signed-in account's connectors (Claude's `claude_ai_*`), the shared home's MCP servers, plugins and skills, exactly as before. That is an accepted risk, like its provider keys: text the Concierge reads (a document, a team's output, a README) can ask it to use the person's accounts. A member never gets these tools, even when the Concierge tells it to do something; see Agents.
- The team marker is `.harness-team`. Deletion removes a directory only when that marker says this platform created it. Pinned by `TeamMarkerTests.A_team_root_carrying_the_marker_is_removed` and `TeamMarkerTests.A_team_root_without_the_marker_is_left_and_named`.
- A team root, a member's workspace and a folder Reset empties are removed one way, `FolderRemoval`, never `Directory.Delete(recursive: true)`: agents create owner-only directories the Host cannot empty, and a recursive delete took the marker first and then failed. The root is emptied around its marker, then the marker goes, then the root; anything left keeps the marker. When the Host switches users (`AgentLaunchUser`), what it cannot remove is removed as the agent with `rm -rf --one-file-system` through the existing launch prefix (no new privilege), only for paths that resolve inside the folder with no symbolic link on the way; links are removed as links and never followed; with no switch there is no agent pass. That pass runs on a worker (`RemoveAsAgent`, which checks the confinement again); with no worker connected nothing is removed as the agent and the removal is recorded unfinished, its reason saying so, and in `control` each worker that joins (not one coming back on its session) retries the unfinished removals once; in `all` the Host's own worker removes its run homes with the worker's `RunHomeRemoval`, never through `FolderRemoval`. Whatever still remains is named path by path in the result (`remaining`), the delete dialog and the tenant log row, and recorded in `unfinished_removals` (`auth-012`); the Host retries every row at start, a person retries from the delete dialog or from the Teams view's list of every unfinished removal - team root, workspace and emptied folder, each with its remaining paths (`GET /api/removals`, `POST /api/removals/retry`), and creating a team over the unfinished removal of a deleted team of the same id finishes it first. A root without its marker is still never deleted, and a folder with no marker is still refused at creation. A retry of a Reset's folder removes only what the Reset named, never what was written since: a named file or link goes only when it was not modified after the row's first `recorded_at` (a link judged as itself, never its target), and one modified since is the member's, kept and no longer counted; a named directory loses only the entries in which nothing was modified after that time, and goes itself only once empty; once a named path is gone, the empty directories above it go too, up to but never including the folder, stopping at a link or a directory modified since, as best-effort clean-up by the Host (one it cannot remove is left in place and never keeps the row unfinished); a retry that takes more than one attempt still clears them: each unfinished attempt records the modification time its own deletes left on every directory it judged unwritten (`unfinished_removals.host_left`, `auth-013`), and a directory still at exactly that time is judged unwritten again, while one written in since has another time and is kept; a named directory the Host still cannot list (the folder itself included) stays unfinished and is never reported finished. Known residual risks: age is the modification time (a file copied in since with its old time kept counts as old), and the Host's pass resolves a directory by path after checking it is not a link, so an agent swapping it for a link in between could redirect the Host's deletes (closing that needs `openat`/`O_NOFOLLOW` deletes). the pass on a worker by `FolderRemovalOnWorkersTests` (`The_agent_pass_is_asked_of_a_connected_worker_with_the_confined_top_level_paths`, `With_no_worker_what_remains_is_recorded_unfinished_with_the_reason`, `The_worker_refuses_a_path_that_is_not_confined`, `A_worker_joining_retries_unfinished_removals_once`, `In_all_a_worker_joining_retries_nothing`), with control and a worker as two processes by `RemovalOnWorkerProcessTests` (`An_agent_owned_owner_only_folder_is_removed_through_the_workers_agent_pass` and `With_no_worker_a_removal_is_recorded_unfinished_and_finished_when_one_connects`, both run only as root and skipped with the reason elsewhere; `With_no_worker_what_the_host_cannot_remove_is_recorded_unfinished_with_the_reason_and_retried_when_a_worker_joins`, run only where the test process cannot switch users), and the Host's own wiring by `Host.WorkerRoleTests.Only_control_retries_unfinished_removals_when_a_worker_joins` and `Host.WorkerRoleTests.All_removes_its_run_homes_with_the_workers_run_home_removal`. - A recursive delete (`Directory.Delete(x, true)`, `recursive: true`, `DirectoryInfo.Delete(true)`) is allowed in `src/` only where agents cannot write inside the folder: when the Host switches users, no process running as `agent` can create an entry anywhere in it. Anywhere they can - a team root and everything in it, a workspace, the documents, the sites folder, any other top-level data entry `prepare-volume.sh` gives to `agent`, anything shared to the agent with write - goes through `FolderRemoval` (`RemoveInsideAsync`, or `RemoveInsideOrThrowAsync` where the old delete threw, bounded so a link on the way is refused). - The cookie name comes from `InstanceIdentity`, a SHA-256 of the data root. `string.GetHashCode` is randomised per process and signs everyone out on every restart. Pinned by `IdentityTests.Cookie_name_is_stable_across_calls`.
- Data Protection keys live in `<dataRoot>/keys`. On Linux there is no DPAPI. The container boundary is the isolation. Do not copy the key directory into a member workspace. When the Host launches children as the separate `agent` user (see `AgentLaunchUser`), they cannot read the key directory, because it is the Host's own. When the Host cannot switch users (dev, tests, an image with no `agent` user), children run as the Host's user and CAN read the keys; that is stated here so nobody "fixes" it by pretending otherwise. The location is pinned by `DataProtectionKeysTests.Keys_are_written_under_the_data_root`. The rest is not pinnable here: nothing copies the key directory today, so a test would assert the absence of a feature, and who can read it depends on the image's owners and modes, not on the code.

## Data

- One data root, one database, one control process. Workers open neither the database nor the key ring and take no data-root lock; `all` is the single-process form (tests, development). `--DataRoot` wins, then `HARNESS_DATA_ROOT`; with neither set the Host refuses to start. Pinned by `DataRootTests.The_setting_wins_over_the_environment_variable` and `DataRootTests.With_neither_set_the_host_refuses_to_start`. The container always sets `HARNESS_DATA_ROOT=/data`, which is a Podman volume; that is the `Containerfile` and the `podman run` line, outside what the test suites run, so it is not pinned.
- The schema migrator must be handed a **superset** of every step it has ever applied. Deleting a step makes a database that already applied it look corrupt. Pinned by `SchemaTests.Every_schema_step_applies_to_an_empty_database` and `SchemaTests.The_migrator_refuses_a_database_holding_a_step_it_was_not_handed`.
- The schema starts from one base step per store (`auth-001`, `messages-001`, `skill-001`, `backlog-001`). A change is a NEW step after those (`backlog-002` is B0025's recorded tips and stored landed; `backlog-003` is B0022's outcome on a backlog item, `backlog-004` is B0028's unrecorded starts); never edit one that has shipped. A volume whose recorded steps are not a subset of the known steps is refused and left alone. Pinned by `ShippedSchemaStepsTests.A_shipped_step_is_never_edited` (each shipped step's SQL is held to its SHA-256; a new step adds a line there), `ShippedSchemaStepsTests.Every_pinned_step_is_still_handed_to_the_migrator`, `FreshVolumeTests.The_steps_are_the_squash_and_the_steps_added_after_it` and `FreshVolumeTests.A_volume_from_before_the_squash_is_refused_and_left_alone`.
- A backlog item's stored key is its citation (`B001F`), minted from `backlog_id_sequence` and never reused. The contract and the route still carry the number; `SqliteBacklogStore` converts at the boundary. Pinned by `FreshVolumeTests.A_backlog_item_is_stored_under_its_citation_and_an_id_is_never_reused`.
- Documents survive team deletion and are listed and readable afterwards; a same-name recreation retires the old folder rather than handing it to the successor. Pinned by `DocumentsRetentionTests.Documents_survive_team_deletion_and_are_listed_and_readable_afterwards` and `DocumentsRetentionTests.A_same_name_team_recreation_retires_the_old_folder`.
- A person may delete any document, a non-empty folder only with `recursive=true` (409 without it), and a gone team's or retired folder's files, folders and whole folder; the whole folder only when its `.harness-team` marker names its team, and never a live team's. Upload and New folder still refuse a gone team. Every delete appends `documents.deleted` to `tenant_events` first, and does not happen when that row cannot be written; a recursive delete in a live team's folder announces each removed file to `FolderWatch`, one announcement per folder. Pinned by `DocumentsDeleteTests` (every case) and `DocumentsDeleteUnrecordedTests.Nothing_is_deleted_when_the_documents_deleted_row_cannot_be_written`; the dialog side by `web/src/components/__tests__/documents-dialog.mount.spec.ts`.
- A person may rename, move and copy documents (`POST /api/teams/{team}/documents/rename`, `/move`, `/copy`, `HumansOnly`, a batch of at most 1000 per request). Each is planned whole before anything is written: a path outside the folder, the marker, a link (never renamed, moved or copied), a folder into itself, a folder holding a link moved to another team, a name clash with no choice, or a write into a gone team's or retired folder is refused with a sentence, and nothing is recorded or done. Moving and copying out of a gone or retired folder is allowed. Each appends `documents.renamed` / `documents.moved` / `documents.copied` to `tenant_events` first, naming every source, destination and replaced path, and does nothing when that row cannot be written. A clash is Keep both (`name (copy)`, `name (copy 2)`), Replace (the existing entry removed through `FolderRemoval.RemoveDocumentsAsync`) or Skip, chosen per item; a name that appears after planning is never overwritten. A copy, or a move to another team, of a folder holding a subfolder the Host cannot list fails that item with "permission denied" and is never done unchecked. A batch that partly fails answers 409, says path by path what was done and what was not, and writes `documents.<verb>-incomplete`; it is never an unhandled error, and nothing goes in `unfinished_removals`. What changed in a live team's folder is announced to `FolderWatch`, once per folder. Dragging and dropping in the Documents dialog calls these same routes and has no route of its own. An upload may name `onClash`: `ask` answers 409 naming the clash, `keep-both`, `replace` (a file only) or `skip`; without it an upload replaces a file of the same name, as it always has. Pinned by `DocumentsRenameTests`, `DocumentsMoveTests`, `DocumentsCopyTests`, `DocumentsChangeRefusalTests`, `DocumentsChangeUnrecordedTests`, `DocumentsChangeIncompleteTests`, `DocumentsUploadClashTests` and `TeamDocumentsFreeNameTests`; the dialog side by `web/src/components/__tests__/documents-explorer-actions.mount.spec.ts` and `documents-drag.mount.spec.ts`.
- A site is published by copying a folder the team may write (its documents folder or its team folder) into `<dataRoot>/sites/<team>/<site>/v<n>`, never linking to it, and the live version is the database's: it changes only after the copy is complete, in one transaction with its `site.published` tenant row, so an agent editing its working copy never changes what a person sees. Links and dot-names are not copied. The last five versions are kept; rollback makes a kept one live, unpublish keeps files and data, delete asks first (409 naming what is lost) and a team deletion removes its sites, their files and their data. Every site change (`site.created`, `site.published`, `site.rolled-back`, `site.unpublished`, `site.deleted`) appends its `tenant_events` row in the same transaction (`SqliteSiteStore`, `TenantAuditRow`); data writes are recorded on the document (`updated_at`, `updated_by`). Data limits - 64 KB a document, 10 000 documents a collection, 50 MB a site - and action limits - a 16 KB payload, a slug name - are refused with a sentence, the data limits checked inside the writing transaction. A member or plugin is a `SiteActor` bound to its own team, and another team's site answers what a missing one does. Pinned by `SitesTests.Publishing_changes_the_live_site_only_once_the_copy_is_complete_and_rollback_restores_the_previous`, `SitesTests.Deleting_a_site_asks_first_and_a_team_deletion_removes_its_sites_and_data`, `SitesTests.Each_limit_is_refused_with_a_sentence` and `SitesTests.A_member_bound_to_another_team_is_refused_as_if_the_site_did_not_exist`.
- A site's generated files live in the team's documents at `sites/<site>/files/`, created with the site (`SiteFiles.Ensure`, best effort, repaired whenever the `site` tool or a plugin run is told it, never by a read), kept when the site or the team is deleted unless empty (`SiteFiles.PruneIfEmpty`: one level at a time, never recursive, never through a link), and listed by the Documents routes like any other documents. The page downloads one under its capability at `_api/files/{path}` only: GET only (every other method 405 before the capability is read), no listing, a path that passes `SiteRules.IsFilePath` (no `..`, no dot-name, no `\`, `%`, `:` or control character), opened from the team's documents folder down with `O_NOFOLLOW` on every component relative to the folder held open above it, so no link is followed at any level, a regular file only, `Content-Disposition: attachment`, a type from `SiteFiles.ContentTypes` (anything else, every type a browser could run among them, is `application/octet-stream`), `nosniff`, `no-store`, no CORS header, under `SitePolicy`. A link and a missing file answer the same 404, and no refusal names an absolute path. - Every human login sees every team. Per-team grants are not an authorization axis and there is no grants table: `auth-001` does not create one. `TeamGate` passes a person straight to the handler, which answers 404 for a team that does not exist; a machine principal is refused a team that is not its own, with the same body a missing team gets. ## Outcomes

An outcome names the business result a workflow serves. `outcomes` and the append-only `workflow_outcome_links` are `outcome-002`, in the log's database file; `triggers.outcome_id` is `auth-017` and `backlog_items.outcome_id` is `backlog-003`; `workflow_ledger.outcome_id_at_close` is the newest link's outcome when the workflow closed. A workflow's outcome is its newest link, followed through `merged_into`. Links are made at the root: a backlog dispatch's `backlog.item.dispatched` row and a trigger's or schedule's fire link from `SqliteMessageStore`'s one insert (`OutcomeLinks.OnAppendAsync`), in the same transaction as that row, attributed to the dispatching person (`how: dispatch`) or the trigger's configurer (`how: trigger`) and never over an existing link; a `tell` without causation that names `outcome` (an id, or the exact name of an active or proposed outcome) links in its append's transaction (`how: tell`). A solution package's trigger may name an outcome by name, and the install creates it `active`. The `outcome` tool (list, show, set, propose) is the Manager's and the Concierge's; `set` and `propose` resolve the workflow as `tell` resolves causation. `outcomes.requireForCompletion` is off by default. A kanban card carries `outcome` (id, name, status): its open workflow's, else its latest workflow's, attached by `CardOutcomes.AttachAsync` after `CardOpenWorkflows.AttachAsync` in ONE query per board read (`IOutcomeStore.CurrentOutcomesAsync`); the board's `outcome` filter (`KanbanFilter.Outcome`, an id or `none`) matches that tag, and the team workflows route stamps the same on each row. ## Solution packages

- A **solution package** (`solution.json` format 1, `docs/solutions.md`) is read only through `SolutionService` and `SolutionChecker`: the check route, the operator's `--solution-check`, the install, the update and the preview all take the same parsed `SolutionPackage`, and none reads the folder a second way. ## Admission

- `wip.maxRunning` (a tenant setting, falling back to `Wip:MaxRunning`) is instance-wide and shared across users. Default: the smaller of the CPU bound `max(1, cgroup CPUs - 1)` (3 when the CPUs are not known) and, when the container has a memory limit (`/sys/fs/cgroup/memory.max`), the memory bound `floor(limit / wip.memoryPerRunMb)`, at least 1; `wip.memoryPerRunMb` is a tenant setting, default 2048 (`Wip:MemoryPerRunMb`). The default is computed on read (`TenantSettings.RunLimit`), so a change to the allowance moves it without a restart and `Program.cs` re-applies the ledger's limit on either change. A row or `Wip:MaxRunning` wins over both bounds. `appsettings.json` ships no `Wip:MaxRunning`; the operator CLI passes `Wip__MaxRunning` only when `maxRunning` is configured (non-zero). ## Containment

- A run's own memory limit is applied from inside the container, never by asking the engine. `RunMemoryLimits` is decided once at start and logged ("Run memory limits: cgroup | rlimit | not available — <reason>", followed by the limit each run now gets), the way `AgentLaunchUser` logs its decision. The decision takes the best mechanism available. **cgroup** needs cgroup v2, the memory controller delegated, and the Host's own cgroup writable (probed by making and removing a child); each run then gets its own `run-<id>` child with `memory.max`, `memory.oom.group` and no swap, and `oom_kill` in its `memory.events` is what says the limit stopped it. Otherwise **rlimit**, and only when a person set `runs.memoryLimitMb` > 0 (`RunMemoryLimit.Set`): with the setting at 0 a run gets NO per-process data limit and no hard ceiling, and the start log says exactly "Run memory limits: not enforced per run - the cgroup is not writable; admission by measured memory guards the container" (`RunMemoryLimits.NotEnforcedLine`). Nothing is computed for it: `RLIMIT_DATA` counts a runtime's virtual reservations, not the memory it uses, and the figure below which a runtime aborts at start depends on the runtime and the CPU architecture, so any computed figure breaks some agent CLI on some machine; admission by measured memory is the guard. With a figure set, `prlimit` from a root-owned system directory, with `--data=N:C` placed AFTER the `AgentLaunchUser` prefix, so it runs with no capability and the agent cannot raise the hard limit: the soft limit N is the run's limit, the hard limit C is `RunMemoryLimits.Ceiling` (`TenantSettings.RunMemoryCeiling`, container limit - Host reserve, or N with no container limit), because raising a hard limit needs CAP_SYS_RESOURCE in the machine's first user namespace, which no rootless engine gives. The agent can raise its own soft limit up to C; C still bounds it. It is per process, not the run's total, and the log line says so. Otherwise **not available**, said plainly. The limit is the tenant setting `runs.memoryLimitMb`, read through a delegate at every launch: 0 (default) is, for a cgroup only, (container limit - `TenantSettings.HostReserveMb`) / `wip.maxRunning`, at least `MinRunMemoryLimitMb`, and none with no container limit; under rlimit 0 is no limit. **A run holding the `heavy` lease gets the heavy allowance** (`RunAllowances`; under rlimit only when a figure is set - a run with no limit has nothing to raise): the container's limit - `HostReserveMb` - the resident memory of every other running run, measured from `/proc` over `RunProcessGroups` when the lease is granted (`TenantSettings.HeavyRunMemoryLimit`), never below its own limit, and its own limit with no container limit; measured rather than a second setting, and not re-read as the others grow. `LeaseActions` reconciles after every acquire, release and run end, so any path that moves the lease through it moves the limit. On cgroup the run's `memory.max` is raised in place; on rlimit `prlimit --pid <pid> --data=<bytes>:` (soft only, run as the agent's user) raises every process in the run's session, so a process already running gets it and everything started after inherits it, up to C. Lowering never kills a run inside its old limit: a cgroup is lowered once `memory.current` less `memory.stat` `file` fits, a process once its `statm` data fits; until then it keeps the raise and the lowering is retried every few seconds. The log line and the `runs.memoryLimitMb` description say what a heavy run gets, and the start log also gives the heavy figure with no other run. **A process the limit stopped while the agent carried on is named** in the run's progress with the limit in force, where it came from and the setting (`RunMemoryLimits.ChildSentence`): with a cgroup a rise in `oom_kill` while the agent lives, polled every 2 s; with an rlimit a transcript line one of whose lines IS the refusal ("Out of memory.", or "<prog>: Cannot allocate memory"; `RunMemoryLimits.ChildOutOfMemory`), followed with `LiveTranscriptReader`. ## Users on the volume

- Two images from one `Containerfile` and one compile: `--target control` (the Host, git, gh, ssh, `sqlite3` for the CLI's backup helper; no Node, no npm, no agent CLI, no install script, a PATH of system folders only, `HARNESS_IMAGE=control`) and `--target worker`, the last stage (today's toolchain, all four scripts, `HARNESS_IMAGE=worker`, no listener), so a build with no target can still run every role. Both are built on one `base` with the three users at fixed ids, so an id means the same user in each: `worker` 10003:10003, in group `agent` and in no group of `harness`'s, runs a worker's Host. On a prepared volume it reads exactly what `agent` can: no host entry. The entrypoint has one branch per role. `all` is as before. `control` prepares the volume and drops to `harness`, with no package and no CLI step; the control image refuses any other role with "This is the control image; it has no agent CLI, so it runs only as control (HARNESS_ROLE=control)." `worker` changes no ownership and makes nothing on the volume: it waits (every 10 s, up to 10 min) until the data root is `harness:agent 0750` with `tmp` and `agent-home` in it, installs the System packages into its own container, installs missing CLIs, makes its state folder `/var/lib/harness-worker` (`worker:worker` 0700, in the container, not on the volume: N workers share the volume, and an agent-writable record of process groups would let an agent choose what a CAP_KILL holder stops), and drops to `worker` with the same three capabilities and `umask 0007`. ## Reset repositories

- **Reset repositories never forces, and never loses what only a person could decide to lose.** It is a team-wide box on the reset dialog, off by default (`TeamResetOptions.ResetRepositories`), and the dialog lists what is lost before the person confirms: each ticked member's worktrees and branches, and the team branch `team/<id>` when every member is ticked (`GET /api/teams/{team}/reset/repositories`, `.HumansOnly()`, reads only). For each ticked member every tree in every team repository - its per-card `wt_<Member>_<key>` trees and a per-member `wt_<Member>` - goes through `WorktreeRemoval.RemoveAsync`, as a member deletion's do: `git worktree remove` without `--force`, then `git worktree prune`. A tree with uncommitted edits or commits on no remote stays, named in the reset result (`repositories.worktreesKept`), the `team.reset` row and the team feed (`repo.worktreeLeft`). Then the member's local branches (its `<member>/` namespace, and with the default branch known whatever its trees had checked out) are deleted with `git update-ref -d` against the measured sha only when every commit on them is on a remote, merged into the default branch or not (nothing is lost; the dialog says so); one holding commits on no remote, or checked out in a tree that was kept, stays and is named the same way (`repositories.branchesKept`, `repo.branchKept`, source the member). `RepositoryReset` is the one place this happens. Pinned by `TeamResetRepositoriesTests.A_ticked_members_clean_trees_and_merged_branches_go_and_dirty_trees_and_unpushed_branches_are_kept_and_named` and `TeamResetRepositoriesTests.The_preview_lists_each_members_trees_and_branches_and_the_team_branch`.
- **The team branch is reset only with every member ticked, and only to the STORED default branch.** Not known refuses the whole reset with `DefaultBranchNotKnown`'s sentence (409) before anything moves, so nothing else changes. In the clone `team/<id>` is moved to the default branch (the local one, else `origin/<default>`) unless it holds a commit on no remote and not on the default branch, is checked out in a kept tree, or is checked out in a clone with uncommitted edits; each of those keeps it, named (`repositories.teamBranchKept`). On origin it is deleted only when it holds nothing `origin/<default>` lacks (ancestry, or `git cherry` with no `+`), judged NEVER on a view that could not be refreshed: origin is asked for both branches (`git ls-remote`) and both are fetched before the compare, and a failed read or fetch keeps it, named. The delete is leased on the sha compared (`GitRunner.DeleteOriginBranchIfAtAsync`: `git push --force-with-lease=refs/heads/team/<id>:<sha> origin :refs/heads/team/<id>`, or `update-ref -d` against that sha for a local origin), so a push landing between the compare and the delete refuses it and the branch is kept, named. Otherwise kept and named. A contributor-mode origin is the fork and is never touched. The default branch itself is never moved, pushed, reset or deleted, on the clone or on origin: no member branch deleted can be it and the team-branch step writes only `team/<id>`. Pinned by `TeamResetRepositoriesTests.With_every_member_ticked_the_team_branch_is_reset_and_kept_on_origin_while_it_holds_work_the_default_branch_lacks`, `TeamResetRepositoriesTests.With_every_member_ticked_a_team_branch_holding_nothing_new_is_deleted_on_origin_and_the_default_branch_never_moves`, `TeamResetRepositoriesTests.While_the_default_branch_is_not_known_resetting_every_members_repositories_is_refused_and_nothing_changes`, and for the fetch and the lease `TeamResetRepositoriesTests.A_team_branch_that_gained_work_on_origin_after_the_clone_last_fetched_is_kept_on_origin_and_named` and `TeamResetRepositoriesTests.The_origin_delete_is_leased_on_the_sha_compared_so_a_push_since_refuses_it`, through the whole reset for a push landing after the compare `TeamResetRepositoriesTests.A_team_branch_that_moved_on_origin_after_the_compare_is_kept_by_the_lease_and_named`, and for a failed read or fetch `TeamResetRepositoriesTests.A_team_branch_origin_could_not_be_asked_about_is_kept_on_origin_and_named` (ls-remote) and `TeamResetRepositoriesTests.A_team_branch_that_could_not_be_fetched_is_kept_on_origin_and_named` (fetch). The contributor-mode fork rule is not pinned: it needs an upstream remote beside the fork, which no fixture here builds.

## Tests

- A test that was not seen to fail for the right reason does not prove the fix.
- A mock in the wrong shape is a confident test. Thirteen green cases while the feature 404s is the failure mode.
- These two are rules for writing tests, so no test can pin them.
- A test Host never starts a real agent. The release runs the suite inside the product image, where the agent CLIs are installed and signed in, and a test that fires a trigger or tells a member would otherwise start a real, paid run with the signed-in account's tools, which outlives its test Host. `AgentCliIsolation` puts a stub of every built-in language-model preset's command (not `bash` or `cat`, which call no model) first on the test process's PATH at load; the stub says why and exits 1. A test that wants a real program names its own command.
