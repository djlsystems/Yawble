# Yawble core: contributor rules

For people and coding agents working on this repository. Rules that are load-bearing, and the failure each one prevents. Most name the test that pins them; keep that test green and keep the rule true when you change the code. For what the product is and how to build it, see `README.md` and `docs/architecture.md`.

The Host runs in a Linux container. An agent child starts in its own session (`setsid`), and its process group is killed when the run ends, so a detached grandchild does not outlive it. A command is resolved once with `PathSearch.Find`, and a miss is a launch failure. The launch lives in `ChildProcess`, which agent and plugin members share. Pinned by `ChildProcessTests`, `ProcessAgentRunnerLaunchTests.The_child_leads_its_own_process_group`, `ProcessAgentRunnerLaunchTests.A_detached_grandchild_does_not_outlive_the_run`, `ProcessAgentRunnerLaunchTests.A_command_not_on_PATH_is_a_launch_failure` and `PathSearchTests.A_missing_command_is_null`.

## Identity

- The code says **Harness**. The product name is **Yawble** and, in code, it appears in exactly two files: `web/src/presentation/product.ts` and the `productName` in `web/package.json`, so renaming the product edits those and nothing that carries identifiers. Pinned by `BrandLeakTests.Brand_strings_stay_out_of_the_code` and `BrandLeakTests.The_brand_lives_in_the_presentation_layer`. The GitHub repository is `djlsystems/Yawble`. The one exception is `cli/`, the operator CLI: its binary is `yawble`, so the brand is its name, and `BrandLeakTests` skips `cli/` by path. The CLI shares this repository's tag, GitHub Release and version number (`v<yyyy.mm.dd.N>`, cut by `scripts/release.ps1` for image and binary together); there is no separate CLI repository. Not pinned: one tag for both is the release script's arithmetic, which `scripts/tests/release-functions.tests.ps1` checks offline, not a behaviour either suite runs.
- Environment variables use the `HARNESS_` prefix. A catalog or team env entry that sets one is dropped, not overwritten: a hand-edited file must not be able to hand a member another principal's credential. Pinned by `AgentEnvironmentTests.Harness_entries_in_a_catalog_or_team_env_are_dropped`.
- A headless child receives only its own provider's key (the command's `credentialVariable` in `auth-probes.json`), plus `GH_TOKEN` when its team has a GitHub remote. Every other provider key, and `GITHUB_TOKEN`, is REMOVED at the spawn site by `AgentEnvironment.ScopeProviderKeys`, not set empty; a key handed in explicitly (a catalog entry's own env, a team env entry) is kept. Pinned by `AgentEnvironmentTests.A_child_receives_only_its_own_provider_key`, `AgentEnvironmentTests.A_team_with_a_GitHub_remote_hands_its_member_GH_TOKEN_and_no_other_foreign_key` and `AgentEnvironmentTests.Copilot_keeps_GH_TOKEN_and_loses_every_other_provider_key`. The Host's own git follows the same rule: `GH_TOKEN` only for an operation on a GitHub team's remote, and a remote given by NAME (`ls-remote origin`, the `repo` refresh) is judged by the team's remotes, not by its spelling, or GitHub refuses the check while Fetch works. Pinned by `LsRemoteTokenTests`. **Not true for the Concierge:** its PTY path merges into the Host's environment and cannot remove a variable (see `AgentEnvironment.MustBeAbsent`), so it still inherits every provider key.
- The team marker is `.harness-team`. Deletion removes a directory only when that marker says this platform created it. Pinned by `TeamMarkerTests.A_team_root_carrying_the_marker_is_removed` and `TeamMarkerTests.A_team_root_without_the_marker_is_left_and_named`.
- The cookie name comes from `InstanceIdentity`, a SHA-256 of the data root. `string.GetHashCode` is randomised per process and signs everyone out on every restart. Pinned by `IdentityTests.Cookie_name_is_stable_across_calls`.
- Data Protection keys live in `<dataRoot>/keys`. On Linux there is no DPAPI. The container boundary is the isolation. Do not copy the key directory into a member workspace. When the Host launches children as the separate `agent` user (see `AgentLaunchUser`), they cannot read the key directory, because it is the Host's own. When the Host cannot switch users (dev, tests, an image with no `agent` user), children run as the Host's user and CAN read the keys; that is stated here so nobody "fixes" it by pretending otherwise. The location is pinned by `DataProtectionKeysTests.Keys_are_written_under_the_data_root`. The rest is not pinnable here: nothing copies the key directory today, so a test would assert the absence of a feature, and who can read it depends on the image's owners and modes, not on the code.

## Data

- One data root, one database, one process. `--DataRoot` wins, then `HARNESS_DATA_ROOT`; with neither set the Host refuses to start. Pinned by `DataRootTests.The_setting_wins_over_the_environment_variable` and `DataRootTests.With_neither_set_the_host_refuses_to_start`. The container always sets `HARNESS_DATA_ROOT=/data`, which is a Podman volume; that is the `Containerfile` and the `podman run` line, outside what the test suites run, so it is not pinned.
- The schema migrator must be handed a **superset** of every step it has ever applied. Deleting a step makes a database that already applied it look corrupt. Pinned by `SchemaTests.Every_schema_step_applies_to_an_empty_database` and `SchemaTests.The_migrator_refuses_a_database_holding_a_step_it_was_not_handed`.
- The schema starts from one base step per store (`auth-001`, `messages-001`, `skill-001`, `backlog-001`). A change is a NEW step after those; never edit one that has shipped. A volume whose recorded steps are not a subset of the known steps is refused and left alone. Pinned by `ShippedSchemaStepsTests.A_shipped_step_is_never_edited` (each shipped step's SQL is held to its SHA-256; a new step adds a line there), `ShippedSchemaStepsTests.Every_pinned_step_is_still_handed_to_the_migrator`, `FreshVolumeTests.The_steps_are_the_squash_and_the_steps_added_after_it` and `FreshVolumeTests.A_volume_from_before_the_squash_is_refused_and_left_alone`.
- A backlog item's stored key is its citation (`B001F`), minted from `backlog_id_sequence` and never reused. The contract and the route still carry the number; `SqliteBacklogStore` converts at the boundary. Pinned by `FreshVolumeTests.A_backlog_item_is_stored_under_its_citation_and_an_id_is_never_reused`.
- Documents survive team deletion and are listed and readable afterwards; a same-name recreation retires the old folder rather than handing it to the successor. Pinned by `DocumentsRetentionTests.Documents_survive_team_deletion_and_are_listed_and_readable_afterwards` and `DocumentsRetentionTests.A_same_name_team_recreation_retires_the_old_folder`.
- A person may delete any document, a non-empty folder only with `recursive=true` (409 without it), and a gone team's or retired folder's files, folders and whole folder; the whole folder only when its `.harness-team` marker names its team, and never a live team's. Upload and New folder still refuse a gone team. Every delete appends `documents.deleted` to `tenant_events` first, and does not happen when that row cannot be written; a recursive delete in a live team's folder announces each removed file to `FolderWatch`, one announcement per folder. Pinned by `DocumentsDeleteTests` (every case) and `DocumentsDeleteUnrecordedTests.Nothing_is_deleted_when_the_documents_deleted_row_cannot_be_written`; the dialog side by `web/src/components/__tests__/documents-dialog.mount.spec.ts`.
- A cursor is **removed**, never zeroed. Zeroing it lets retention get stuck behind it. Pinned by `CursorRemovalTests.A_forgotten_cursor_no_longer_holds_retention_back` and `CursorRemovalTests.Forgetting_the_last_cursor_leaves_no_position_rather_than_zero`.
- A team repository's default branch is stored, never assumed. `auth-006` keeps two columns per repository in `team_repo_default_branches`: `from_remote`, what `git remote set-head origin --auto` read on the last clone or successful Fetch (NULL when that read fails or HEAD names no branch), and `set_by_person`, a choice from Team settings that no Fetch touches and that wins until cleared. No row, or NULL in both, is not known: every Git action that needs the branch (bring current, rebase, push, merge to main, delete the team branch, ask the team, landed) answers 409 or `unknown` and changes nothing, and the publisher never pushes it. A failed Fetch leaves a stored value, or not known, as it was. Nothing backfills `main`, and the clone folder stays `repos/<Repo>/main`. At start, a clone whose `from_remote` is NULL is read once from the `refs/remotes/origin/HEAD` it already holds, with no network (`DefaultBranchAtStart`), so an existing clone is not left not known until a person presses Fetch; a clone with no such ref stays not known. Pinned by `DefaultBranchAtStartTests.A_clone_with_no_stored_branch_is_read_at_the_next_start`. `set-head --auto` asks origin, so it gets `GH_TOKEN` by the team's remotes as a fetch does; without it a private repository refuses the read and every Fetch would write not known over the stored branch. Pinned by `LsRemoteTokenTests.The_default_branch_read_of_a_GitHub_teams_origin_is_handed_the_token`. Pinned by `RepoDefaultBranchTests`, `FreshVolumeTests.A_repository_from_before_the_default_branch_step_is_not_known_afterwards` and `PublisherRejectionTests.The_stored_default_branch_is_never_published`; the web side by `repoStatus.spec.ts`, `repoLadder.spec.ts` ("the stored default branch") and `team-settings-default-branch.mount.spec.ts`.
- Contributor mode is per repository. `auth-007` keeps a row in `team_repo_contributors` per repository: an optional `upstream_url` (set: the repository's own URL is the fork, `origin`), `fork_owner`, `dco_sign_off`, `cla_signed_note` and the recorded pull request (URL, number, state, read-at). The clone gets an `upstream` remote beside origin; setting or clearing the upstream adds, re-points or removes that remote and nothing else, and a clone made later gets it when it is made. Fetch fetches both; Bring current and Rebase use `upstream/<default>` and still stop when the default branch is not known. Bring current also syncs the fork - `git push origin upstream/<default>:refs/heads/<default>`, never forced, the ONE push of a default branch the platform makes and only from upstream - and refuses a fork whose `<default>` has commits upstream lacks, naming the count and changing nothing. `repo.forkSynced` is appended after that push. "Sign off commits (DCO)" writes a marked `commit-msg` hook into the clone's `.git/hooks` (worktrees share it) using `git interpret-trailers --if-exists doNothing` with the instance's `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`; turning it on without them is refused naming the fix (the operator CLI's `secret set GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL`), and a hook the platform did not write is never replaced or removed. Agents get no new tool, skill text or environment, and never push, fork or open a pull request. Pinned by `ContributorModeTests`, `FreshVolumeTests.A_repository_from_before_the_contributor_step_is_owned_afterwards`; the web side by `contributor.spec.ts`, `team-settings-contributor.mount.spec.ts`, `create-team-dialog.mount.spec.ts` and `repo-card-states.mount.spec.ts`.
- Contributor mode's GitHub buttons are a person's only: Merge to main answers 409 in contributor mode and the Git dialog offers Open pull request instead (`gh pr create --repo <upstream> --head <fork-owner>:team/{id} --base <default>`, title and body edited first), refused while the default branch is not known, while team/{id} is not on the fork, and - DCO on - while any commit since `upstream/<default>` lacks Signed-off-by, naming them; an open one is linked, never doubled; `repo.pullRequestOpened` is appended after GitHub opened it. Fork it for me is `POST /api/github/fork` (`gh repo fork --clone=false`, `--org` only when given). Landed in contributor mode is the recorded pull request's state (`in-review`, `declined`, `landed`; unreachable or refused is `unknown`), asked when the backlog or Git dialog is read and at most once a minute per pull request (`PullRequestStateReader`). GitHub is reached only through `IGitHubContributor`; tests fake it and never call GitHub. The operator CLI's `github` and `doctor` say contributor mode needs a classic token with `public_repo` (`repo` for a private upstream). Pinned by `PullRequestTests`; the web side by `repoLadder.spec.ts`, `repo-card-states.mount.spec.ts`, `backlog.spec.ts` and `fork-it-for-me.mount.spec.ts`.
- Ordering between a git push and the row that records it is the whole guarantee. Publish the branches, then append the row. Pinned by `PublishOrderTests.The_pushed_row_is_appended_only_after_its_branch_is_on_origin`.

## Authorization

- Every human login sees every team. Per-team grants are not an authorization axis and there is no grants table: `auth-001` does not create one. `TeamGate` passes a person straight to the handler, which answers 404 for a team that does not exist; a machine principal is refused a team that is not its own, with the same body a missing team gets. Pinned by `TeamGateTests.A_container_reaches_its_own_team`, `TeamGateTests.A_container_is_refused_another_team_with_the_body_a_missing_team_gets` and `TeamGateTests.A_person_on_a_missing_team_gets_the_handlers_404`.
- **Verb permits stay.** They bound machine principals. Collapsing "which team" and "which verb" is the change to refuse. A member credential must not perform tenant administration. Pinned by `PermitTests.A_container_key_is_refused_tenant_administration` and `PermitTests.A_person_may`.
- Every endpoint carries exactly one of `RequirePermit`, `NoPermitRequired` or `HumansOnly`. Pinned by `RouteMarkerTests.Every_endpoint_carries_exactly_one_marker`.
- `{team}` stays in the route. It tells the handler which team to act on. It is not an access-control key for humans. The second half is pinned by `CrossTeamTests.A_person_and_a_concierge_reach_every_team`. That the segment stays is a route-design decision with no behaviour of its own to assert, so it is not pinned.
- A container principal is bound to its own team. That is identity, not a grant. There is no tenant-scoped team. A person, a person's key and the tenant Concierge reach every team that exists. Pinned by `CrossTeamTests.A_container_reaches_its_own_team`, `CrossTeamTests.A_container_is_refused_another_teams_verb_with_what_a_missing_team_gets`, `CrossTeamTests.A_person_and_a_concierge_reach_every_team` and `CrossTeamTests.A_container_sees_only_its_own_team_in_the_overview`.
- `users.current_team` is per person, not per credential. The browser and the Concierge are two principals for one human. Pinned by `UserCurrentTeamTests.A_team_chosen_in_the_browser_is_the_team_the_persons_key_reads_and_back` and `UserCurrentTeamTests.The_current_team_survives_a_credential_rotation`.

- Failed sign-ins are limited, successful ones never are. `LoginThrottle` counts FAILED `POST /api/auth/login` per typed account (10 in 15 minutes) and per client address (100, because behind the tunnel every visitor shares one address); past either, every attempt answers 429 with a sentence in `error` for a five-minute cool-down, the right password included, or the 429 would mark only wrong guesses. A success clears that account's count. Pinned by `LoginThrottleTests.Eleven_wrong_passwords_for_one_account_in_a_minute_get_a_429`, `LoginThrottleTests.The_right_password_from_three_devices_is_never_limited`, `LoginThrottleTests.One_locked_account_does_not_lock_another_behind_the_same_address` and, for the front door showing the sentence, `auth-form.mount.spec.ts`.
- Every response carries `nosniff`, `Referrer-Policy: same-origin`, `X-Frame-Options: DENY` and a self-only CSP whose one loosening is `style-src-elem 'unsafe-inline'` for xterm (measured in Chromium; `SecurityHeaders` says why). The one exception is stricter, not looser: every `documents/view` response, PDF included, carries a sandboxed CSP IN PLACE OF the app's (`sandbox; default-src 'none'; ...`, and exactly `sandbox; default-src 'none'` for PDF), so an uploaded HTML page renders with no script and an opaque origin; it is set through `SecurityHeaders.PolicyOverride` and nothing else may replace the CSP. Pinned by `HealthAndHeadersTests.Every_response_carries_the_security_headers` and `HealthAndHeadersTests.A_documents_view_response_carries_the_sandboxed_policy_in_place_of_the_apps`. That the app runs with no violations is a browser check, not a test in either suite.
- `/healthz` is anonymous and outside the SPA rewrite, and reports database, data root and pump; the image's `HEALTHCHECK` curls it, which podman keeps only with `--format docker`. Pinned by `HealthAndHeadersTests.Healthz_is_anonymous_and_names_three_passing_checks` and `HealthAndHeadersTests.A_pump_that_has_not_beaten_for_a_minute_is_not_alive`.

## The log

- The container subscribes, not the agent. The agent exits; the container holds the subscription. Pinned by `ContainerSubscriptionTests.A_container_whose_agent_has_exited_is_woken_by_the_next_instruction`.
- The ledger is a projection of the message log. Context comes from the ledger, not the transcript. Pinned by `LedgerContextTests.The_next_runs_context_holds_the_last_runs_output_and_not_its_progress`.
- Message types match under binary collation. Build an instruction type from the **found** container id, not the caller's spelling, or the call returns 200 and wakes nothing. Pinned by `InstructionSpellingTests.A_tell_spelled_in_another_case_is_addressed_to_the_registered_container`.
- A container does not react to its own publications, and it is woken only by its own team. A null team fails closed. Pinned by `HandbackWakesOnceTests.Two_teams_managers_never_wake_each_other`, `HandbackWakesOnceTests.A_container_is_not_woken_by_its_own_row` and `NullTeamTests.A_row_whose_team_cannot_be_read_wakes_nobody`.
- `container.progress` stays on the log and out of the ledger. `container.blocked` stays in the ledger. Pinned by `LedgerExclusionTests.Progress_stays_on_the_log_and_blocked_stays_in_the_ledger`.
- A Manager is woken **once per finished run**. It holds both `handback` and `completed`; a worker that handed back has already woken it, so its `completed` row carries `handedBack: true` and the pump passes a subscriber over on it when that subscriber also holds `handback`. A subscriber holding only `completed` still wakes. Otherwise a Manager runs twice per delivery and the second run is refused its own `workflow_complete`. Pinned by `HandbackWakesOnceTests.A_worker_that_hands_back_wakes_its_manager_once`, `HandbackWakesOnceTests.A_worker_that_does_not_hand_back_still_wakes_its_manager_on_completion` and `HandbackWakesOnceTests.A_subscriber_holding_only_completed_still_wakes_on_a_handed_back_run`.
- The completion payload field is named `output`. Renaming it blanks the feed and the agent-facing text together. Pinned by `CompletionPayloadTests.A_finished_run_publishes_its_output_under_output`.
- A run whose agent never called the platform is not a success. `CredentialUseRunner` compares `principals.last_used_at` before and after. Null means not measured, and not measured is not a failure. The decorator in `Program.cs` is what makes the check real. Pinned by `AgentRunnerCompositionTests.A_run_that_used_its_credential_reached_the_platform`, `AgentRunnerCompositionTests.A_run_that_never_called_the_platform_and_left_no_evidence_is_not_a_success`, `AgentRunnerCompositionTests.A_store_that_cannot_answer_is_not_measured_and_not_a_failure` and, for the decorator, `HostAgentRunnerTests.The_hosts_agent_runner_is_the_credential_use_decorator`.
- `workflow.completed` is declared by the owner of that correlation. Busy means busy **in that correlation**, or parallel workflows on one team deadlock. A correlation of 0 is refused. Pinned by `WorkflowOwnerTests.The_owner_is_the_container_the_root_instruction_addressed` and `WorkflowCompleteRouteTests.A_member_running_no_workflow_is_refused_a_declaration`. "Busy in that correlation" is not pinned: `WorkflowBusyState` is internal to Harness.Host, which grants the test assembly no internals, and reaching it through the route needs two real runs in flight at once in one Host.
- Causation joins a workflow. Omitting it roots a new one. `PUT /api/me/steering` writes the highlighted workflow, the next launch copies it to `HARNESS_CAUSATION`, and `STEERING.md` is what a Concierge already running can read. Pass that number as `causation` on `tell`. Pinned by `TellCausationTests.A_named_causation_is_kept`, `TellCausationTests.A_container_that_names_no_causation_dispatches_inside_its_run`, `TellCausationTests.A_person_or_concierge_that_names_none_starts_a_workflow`, `SteeringRouteTests.The_steering_route_records_the_persons_highlighted_workflow` and `SteeringLaunchTests.The_next_concierge_launch_carries_the_steered_workflow`.

- A repository the platform could not clone roots a notice workflow to the Manager, carrying `repoNotReady` (the clone paths). When a person makes that clone later with Fetch or Bring current, `RepoReadyNotice` tells the Manager inside every such workflow still open, or its block outlives the clone. Pinned by `FetchMakesAMissingCloneTests.Fetch_makes_a_clone_that_failed_when_the_repository_was_attached` and `FetchMakesAMissingCloneTests.A_clone_made_later_tells_the_manager_in_the_workflow_the_failure_opened`.

- A folder-change trigger never delivers. It polls, publishes `file.changed`, and the event arm of the pump fires it; a poll's row (source `trigger:<id>`) wakes only the trigger that polled, or two members watching one folder each wake twice. A pure touch does not fire: what fires is a diff by name and size, and the mtime in the fingerprint only restarts the quiet period. Changes made while the team ran are folded into the baseline. Pinned by `FolderChangeTriggerTests.A_poll_published_row_wakes_only_the_trigger_that_polled`, `FolderChangeTriggerTests.A_touch_with_no_content_change_does_not_fire` and `FolderChangeTriggerTests.The_woken_member_writing_into_the_same_folder_does_not_fire_again_within_the_minimum_interval`.

## Usage

- Nothing is estimated. Unknown stays unknown. Pinned by `UnknownUsageTests.A_run_that_reports_no_usage_publishes_no_token_figures_and_is_counted_as_unmeasured` and `UnknownUsageTests.A_combined_total_leaves_the_split_unknown`.
- `tokensIn` is uncached input. Cache reads are `tokensCachedIn` and are **not** added into `tokensIn`. Counting them at full weight inflates spend many times over. Pinned by `UsageBillableTests.Cache_reads_are_not_full_price_input` and `UsageBillableTests.Cached_input_may_exceed_uncached_input`.
- Spend uses `InvocationUsage.BillableTokens`: cache reads at 1/10, cache writes (`tokensCacheCreation`) at 5/4, a combined total (codex) as reported. The SQL in `SqliteMessageStore.SpendAsync` must stay on those same integer weights. Pinned by `UsageBillableTests.Cache_writes_bill_at_five_quarters`, `UsageBillableTests.A_combined_total_is_not_reweighted`, and for the SQL by `SpendSqlTests.Cache_reads_are_weighted_as_BillableTokens_weights_them`, `SpendSqlTests.Cache_writes_are_weighted_as_BillableTokens_weights_them` and `SpendSqlTests.A_combined_total_is_counted_as_BillableTokens_counts_it`.
- A run is billed once, however many deliveries it answered. A batched run closes each delivery with its own terminal row; only the first carries the token figures, the rest carry `usageCountedOn` and no figures, and both spend queries skip them. Otherwise a Manager that answers two hand-backs in one run is charged twice. Pinned by `BatchedRunUsageTests.A_run_that_answers_two_deliveries_is_billed_once`.
- A workflow budget reads spend **since the last nudge**, and the wake uses that same figure. Two different figures refuse a dispatch the pump would have allowed. Pinned, for the window and the pump, by `WorkflowBudgetAtTheWakeTests.Spend_since_the_nudge_counts_only_runs_after_it` and `WorkflowBudgetAtTheWakeTests.A_wake_over_the_bound_is_refused_and_a_nudge_lets_the_next_one_run`. The `tell` route's copy of the check is not pinned separately; it calls the same `GetSpendSinceNudgeAsync`.

## Agents

- An agent is how to launch. A prompt is what to say. Nothing in code names a preset. `{mcpConfig}` is a launch token, not a branch on `claude`. Grok's `config.toml` is written only when its harness entry is missing or points at another URL. Pinned by `McpLaunchConfigTests.An_entry_grok_rewrote_that_already_points_here_is_not_rewritten`, `McpLaunchConfigTests.The_grok_entry_follows_the_host_that_launched_it` and `McpLaunchConfigTests.A_grok_config_with_no_harness_entry_gets_one_and_keeps_the_rest`. No source scan for preset names pins the rest: `McpLaunchConfig` still names grok's config file, and `auth-001` still seeds `claude` (which `auth-003` turns into NULL).
- Built-ins come from the build. The Concierge, Manager and Member prompts, the built-in skills and the built-in presets are compiled into the host and never written to the volume; the skill index is rebuilt from the build on every start, and every route refuses to edit, rename or delete a built-in, or to give a custom skill a built-in's name. Pinned by `BuiltInsFromTheBuildTests.No_route_edits_deletes_or_shadows_a_built_in_skill`, `BuiltInsFromTheBuildTests.A_built_in_preset_is_listed_read_only_and_refused_when_sent_back_changed`, `BuiltInsFromTheBuildTests.A_fresh_volume_holds_no_skill_files_and_no_catalog_file` and `SkillMigrationTests.Rebuilding_the_built_ins_takes_the_builds_text_and_keeps_every_custom_skill`. A volume that holds skill files has them moved to `backups/skills-before-builtins` at start, never deleted: `SkillMigrationTests.Skill_files_on_a_volume_are_moved_to_the_backup_and_only_the_custom_ones_imported`.
- The one exception is a built-in preset's tags: the tenant setting `agents.tags` (preset name to its list of tags) overrides them instance-wide, and `AgentCatalog` applies it through a delegate wherever tags are read - `GET /api/agents` (with `tagsFromOperator` and `buildTags`), the hiring view and the next hire - with no restart. Removing an entry resets the build's tags; an entry naming no built-in is ignored and listed as `ignoredTagOverrides`, never an error. `PUT /api/agents` accepts a built-in sent back with the build's or the operator's tags, and refuses any other change. Pinned by `BuiltInTagOverrideTests.A_built_ins_tags_can_be_changed_and_the_next_hire_uses_them_without_a_restart`, `BuiltInTagOverrideTests.Resetting_removes_the_override_and_the_builds_tags_return`, `BuiltInTagOverrideTests.An_override_for_an_unknown_preset_is_ignored_not_fatal_and_says_so`, `BuiltInTagOverrideTests.An_invalid_value_is_refused_naming_the_field_and_nothing_is_written`, `BuiltInTagOverrideTests.The_write_appends_a_tenant_events_row`, `BuiltInTagOverrideTests.The_override_is_not_written_when_its_audit_row_cannot_be` and `BuiltInTagOverrideTests.A_built_in_sent_back_with_its_operator_tags_is_accepted_and_any_other_change_is_still_refused`. On the Agents screen a built-in row offers "Edit tags" and "Reset to the build's tags" (only when the tags are the operator's) and no other control; both write `agents.tags` through `PUT /api/tenant/settings`, re-reading the map and moving only that preset's entry, never a changed catalog. Pinned by `web/src/components/__tests__/agents-dialog.mount.spec.ts` ("offers tag editing on a built-in and nothing else…", "writes a built-in's new tags to agents.tags…", "…resets a built-in by removing its entry").

## Members

- The member runtime is generic; what it runs is behind `IMemberRunner`. `MemberRuntime` (formerly `AgentContainer`) and `ContainerHost` hand the work over as data and read a `MemberResult`. They build no prompt and no history, and they word no agent failure. `AgentMemberRunner` does all of that for agents, over the unchanged `CredentialUseRunner(ProcessAgentRunner)` stack. An agent member's rows, prompt, context, environment, persisted row and snapshot are byte-identical to the step-0 goldens. Re-record them only with `HARNESS_UPDATE_GOLDENS=1`, and only for a change meant to be visible. Pinned by `MemberGoldenTests` and `MemberRuntimeTests.The_runtime_and_the_pump_name_no_agent_seam`.
- What a member runs is read from `team_members.agent` through `MemberRef`, and only there: a bare name is an Agent preset, `plugin:<id>` is a plugin. `MemberRunnerRouter` picks the runner per invocation. No plugin code goes in `Harness.Containers`. Rename C# types freely; never rename `agentContainer.*`, a `ContainerSnapshot` field or a route. Pinned by `PluginMemberEndToEndTests.P7_Nothing_plugin_specific_is_in_the_pump` and `PluginMemberRegistryTests`.

It runs through `ChildProcess` with an allowlisted environment, speaks `harness.member/1` on stdin/stdout, and reports through `MemberReports`, the same code the MCP routes run. Its secrets are logical keys, resolved from the Host environment at each run and passed only on stdin. See `docs/plugins.md`. Pinned by `PluginMemberRunnerTests`, `PluginCatalogTests` and `MemberReportsTests`.

## Admission

- `wip.maxRunning` (a tenant setting, falling back to `Wip:MaxRunning`) is instance-wide and shared across users. Default `max(2, cgroup CPUs)`, else 4. `0` is unlimited (`WipLedgerTests.Zero_is_unlimited`). The setting and its fallbacks are pinned by `TenantSettingsTests.A_row_wins_over_appsettings_which_wins_over_the_built_in_default`, `TenantSettingsTests.The_default_running_limit_is_the_cpu_count_when_that_is_above_two` and `TenantSettingsTests.The_cgroup_cpu_limit_is_read_from_cpu_max`. The "else 4" arm is not pinned: with no CPU count passed, `TenantSettings` reads the real `/sys/fs/cgroup/cpu.max`, and there is no seam to make it read nothing. The container memory limit does not replace it; that is a statement of intent, not a behaviour. It changes at runtime through `WipLedger.SetMax`, under the ledger's lock; lowering it evicts nothing. Pinned by `WipClaimTests.Raising_the_limit_at_runtime_starts_waiting_work_without_a_release` and `WipClaimTests.Lowering_the_limit_at_runtime_evicts_nothing_and_holds_the_next_start`.
- Work that cannot start is **waiting**, not failed. Nothing is refused, `tell` is never held, and there is no `wait` tool. `GET /api/wip` names who is running and who is waiting, by team and member; `ContainerSnapshot.Held` marks the container, and `/api/teams/rollup` counts both per team. A person blocked by a colleague's run must be able to see that it is a colleague's run. Pinned by `WipLedgerTests.The_cap_holds_work_and_names_who_has_the_slots`, `TellNeverHeldTests.A_tell_into_a_full_pool_answers_at_once_and_the_run_waits_visibly`, `LimitLoweredAcceptanceTests.Lowering_4_to_2_with_six_runnable_members_runs_two_and_queues_four_in_order`, `HeldTeamRollupTests.A_team_whose_manager_waits_for_a_slot_reads_waiting_for_a_slot`, `WipClaimTests.Work_over_the_cap_waits_and_starts_when_the_slot_is_released` and `WipClaimTests.A_held_claim_shows_on_the_snapshot_until_the_run_starts`.
- A paused team takes no slot and holds no place in the queue: its waiting work is passed over for a released slot. Pinned by `WipClaimTests.A_paused_team_is_passed_over_for_a_released_slot`.
- A released slot goes to whoever has waited longest (FIFO). The claim loop waits on `WipLedger.Changed`, never a poll. Pinned by `WipClaimTests.A_released_slot_goes_to_the_longest_waiter` and `WipClaimTests.Released_slots_go_to_waiters_in_the_order_they_queued`.
- A Manager has one reserved slot above the limit, so a pool full of members never starves the Manager that would free them. Pinned by `WipClaimTests.A_manager_is_not_held_behind_its_workers`, `WipClaimTests.A_pool_full_of_members_still_starts_a_manager_wake` and `WipClaimTests.A_manager_uses_one_reserved_slot_and_no_more`.

## Settings

- Instance-wide settings are `tenant_settings` rows over `appsettings.json` over built-in defaults, read once at start and held by `TenantSettings`. A consumer is handed a delegate, never a number: a value captured in a constructor brings the restart back. Every write appends a `tenant_events` row, in the same transaction. Pinned by `TenantSettingsTests.A_write_applies_without_a_restart_and_appends_an_audit_row` (a write takes effect without a restart, for `wip.maxRunning` and the workflow budget, and appends the audit row), `TenantSettingsTests.A_value_is_not_written_when_its_audit_row_cannot_be`, `TenantSettingsTests.A_row_wins_over_appsettings_which_wins_over_the_built_in_default` and `TenantSettingsTests.An_invalid_value_is_refused_naming_the_field_and_nothing_is_written`. "A delegate, never a number" is not pinned as a rule over every consumer: whether a constructor captured a value is visible only by exercising each consumer after a write, and only the two above are exercised.

- "System packages" (`system.packages`) is the one setting that applies at the next START, not at once: the entrypoint installs it with `apt-get` as root before the host runs, so the host copies the list to `<dataRoot>/system-packages` at start and on every change, and the entrypoint reads that file, never the database. A name is checked against the same pattern twice, by `SystemPackages.IsValidName` and by `scripts/prepare-volume.sh`, because the file reaches a root shell; a failed install is logged and the host starts anyway. Pinned by `SystemPackagesSettingTests.A_change_is_written_to_the_file_the_entrypoint_reads`, `SystemPackagesSettingTests.A_name_that_is_not_a_package_name_is_refused_and_nothing_is_written`, `SystemPackagesSettingTests.The_list_survives_a_restart_and_the_file_is_rewritten_from_it`, `PrepareVolumeTests.Only_valid_package_names_reach_apt_get_and_nothing_else_is_run` and `PrepareVolumeTests.A_failed_install_is_logged_and_the_entrypoint_starts_the_host_anyway`.

## Users on the volume

- Two users, fixed ids: `harness` 10001:10001 runs the host and is also in group `agent`; `agent` 10002:10002 runs agent children and the Concierge PTY (the host finds it by name). The entrypoint starts as root, sets ownership on every start (`scripts/prepare-volume.sh ownership`: host files `messages.db*`, `keys`, `agents.json*`, `agent-launch.json*` (what `--doctor` reports as agentLaunch), `logs`, `backups`, `host.lock*`, `system-packages*` are harness-only 600/700; everything else, and any `FileBrowser__Roots__<n>__Path` outside the volume that, resolved with `realpath -e`, is not a system directory (`/var/*` included), is agent's with directories `g+rwxs` and files `g+rw`; inside `agent-home` only the owner changes, except that the home itself and `.grok` (directory `g+rwxs`, files directly in it `g+rw`) are the group's so the host can rewrite grok's `config.toml`; the Claude login, `.ssh` and the rest keep their modes, because ssh refuses a group-readable key), sets `safe.directory '*'` and the GitHub credential helper in the SYSTEM git config (root never writes into the shared HOME) and `/tmp` 1777, then drops to `harness` with `umask 0007` (not 0002: files the host creates in the 0750 data root between starts must not be readable by agent) and setpriv keeping only CAP_SETUID, CAP_SETGID and CAP_KILL in the ambient and bounding sets. KILL is there because a process of another user refuses the host's signal without it: a watchdog or Stop could not end an agent. The data root is harness:agent 0750, so `agent` cannot create a top-level entry: one it needs is made by the entrypoint first. Root finds commands in the system folders only (the entrypoint's first command and prepare-volume.sh set that PATH), and the host's PATH, like the image's ENV, puts the system folders before every agent-writable tool folder (`/data/bin`, `npm-global/bin`, ...): otherwise a `find` or `git` an agent plants there runs as root or as the host; setpriv and dotnet are called by absolute path. Root also reads no user config from `agent-home`, which agent owns: both scripts set `HOME=/root`, `GIT_CONFIG_GLOBAL=/dev/null` and `PYTHONNOUSERSITE=1` and unset the XDG folders before their first command, because root's git would read agent's `.gitconfig` (a malformed one stops the boot) and python3 in an apt maintainer script would import agent's `usercustomize.py` as root; only the CLI install and the host exec get `HOME=/data/agent-home` back, on their own lines. The image's `ENV HOME` stays agent-home for `podman exec` logins and `--doctor`. Pinned by `PrepareVolumeTests.Root_runs_on_system_folders_only`, `PrepareVolumeTests.Root_reads_no_gitconfig_or_python_user_site_from_the_agents_home`, `PrepareVolumeTests.A_command_planted_on_the_callers_path_is_not_run`, `PrepareVolumeTests.An_all_root_volume_gets_the_host_files_for_harness_and_everything_else_for_agent`, `PrepareVolumeTests.A_second_start_changes_nothing`, `PrepareVolumeTests.A_file_browser_root_outside_the_volume_is_agents_and_a_system_directory_is_refused`, `PrepareVolumeTests.The_entrypoint_sets_ownership_and_installs_packages_as_root_then_drops_to_harness`, `PrepareVolumeTests.The_host_keeps_only_setuid_setgid_and_kill_and_its_agent_children_keep_nothing` (runs the exec line for real when the suite is root), `PrepareVolumeTests.Nothing_but_chmod_1777_touches_tmp`, `PrepareVolumeTests.A_script_run_by_these_tests_sees_only_the_environment_it_is_given` (a runner's `FileBrowser__Roots__*` never reaches a real chown) and `PrepareVolumeTests.The_image_carries_both_users_at_fixed_ids_and_the_tools_to_switch`. Every tarball the image unpacks into a system folder is unpacked `--no-same-owner`: otherwise the Node tarball keeps its uid 1001, and `/usr/local/bin`, `node` and `npm` belong to a user the image does not have. Pinned by `PrepareVolumeTests.Every_tarball_the_image_unpacks_is_owned_by_root`. That the users exist in a built image is not pinned: neither suite builds the image.

## Tests

- A test that was not seen to fail for the right reason does not prove the fix.
- A mock in the wrong shape is a confident test. Thirteen green cases while the feature 404s is the failure mode.
- These two are rules for writing tests, so no test can pin them.
- `dotnet test` on this repo's Microsoft.Testing.Platform projects can report "zero tests" even when the assembly has tests. Run the test dll directly: `dotnet tests/Harness.Tests/bin/Debug/net10.0/Harness.Tests.dll` after a build. This describes the tooling, so it is not pinned.
- A rule above that names no test has none. A rule marked **Currently VIOLATED** is pinned by a Skipped test that fails when un-skipped; the fix removes the Skip. A rule that cannot be pinned says so, and why.
