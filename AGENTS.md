# Yawble core: contributor rules

For people and coding agents working on this repository. Rules that are load-bearing, and the failure each one prevents. Most name the test that pins them; keep that test green and keep the rule true when you change the code. For what the product is and how to build it, see `README.md` and `docs/architecture.md`.

The Host runs in a Linux container. An agent child starts in its own session (`setsid`), and its process group is killed when the run ends, so a detached grandchild does not outlive it. A command is resolved with `PathSearch.Find`, and a miss is a launch failure once the launch has looked again for about 30 seconds. The launch lives in `ChildProcess`, which agent and plugin members share. Pinned by `ChildProcessTests`, `ProcessAgentRunnerLaunchTests.The_child_leads_its_own_process_group`, `ProcessAgentRunnerLaunchTests.A_detached_grandchild_does_not_outlive_the_run`, `ProcessAgentRunnerLaunchTests.A_command_not_on_PATH_is_a_launch_failure` and `PathSearchTests.A_missing_command_is_null`.

A program missing at launch is not an agent fault. The shared install every member launches from is replaced in place while a CLI updates, so a launch can find no program for a few seconds. `ChildProcess.FindAsync` looks again every few seconds for about 30 (`LaunchLookup`, injectable so tests do not wait), and a program that appears is launched as normal with nothing recorded but one progress line. One that never appears fails with the class `launch-missing`, whose words say the program was not found when the run started, may be being installed or updated, and that re-sending the instruction will try again; they ask nobody to repair anything. The Manager prompt and skill say such a failure is re-sent, and escalated to a person only when it has already happened twice. Pinned by `LaunchMissingTests.A_program_missing_at_launch_that_appears_two_seconds_later_starts_the_run_normally`, `LaunchMissingTests.A_program_that_never_appears_fails_launch_missing_and_is_not_an_agent_fault` and `LaunchMissingTests.The_Managers_context_for_a_launch_missing_failure_says_re_send_and_names_nobody_to_repair_anything`.

An agent CLI updates only when the platform says so. The install is shared, so every launch the Host makes of a built-in self-updating CLI (a member, the Concierge's terminal, the sign-in probe, the tool pre-flight's listing) carries its preset's `updates` declaration, which turns the CLI's own updater off. That is a variable set after the preset's and team's env, or for codex a `-c` argument placed after the launch's own. The one exception is codex's pre-flight listing (`mcp list`, `features list`, `debug prompt-input`), which carries only the environment: codex's key is a launch argument those listing subcommands never act on, and they neither check for nor download an update. Updates happen at the container's start (`ensure-agent-clis.sh`, before the Host) and when a person asks (`POST /api/agents/{name}/update`). An update the Host runs goes through `AgentUpdateGate`: it waits for that command's runs in flight, and new launches of it wait for the update. They are held, never failed. A member's launch carries both this and its preset's isolation, neither replacing the other. Pinned by `AgentUpdatesTests.Every_launch_of_a_self_updating_preset_carries_its_update_off`, `AgentUpdatesTests.The_Concierges_terminal_carries_the_update_off`, `AgentUpdatesTests.A_members_launch_sets_the_update_off_last_so_no_preset_or_team_env_turns_it_back_on`, `AgentUpdatesTests.A_members_launch_carries_its_isolation_and_its_update_off`, `AgentUpdatesTests.A_members_process_gets_the_isolation_and_the_update_off_variables_together`, `AgentToolPreflightTests.A_member_is_listed_with_its_isolation_and_the_concierge_without_it` and `AgentUpdatesTests.A_platform_update_waits_for_the_run_in_flight_holds_a_new_launch_and_that_launch_then_starts`.

The Agents screen shows each built-in preset's CLI version, when it last changed and who brought it (a container start, or a person named by email), read from the Host's CLI version record (`cli-versions.jsonl`), the one `yawble doctor` and `yawble agents` read. Nothing is estimated: a version the record lacks reads "version not known", and a record that never saw the version change says how far back it looked instead of an update time. `GET /api/agents` gives it to a person as `cliVersions` (a machine principal gets none), and a finished update's `result` carries the entry as `cliVersion` after writing its own line, which the row shows in place, saying so when the version did not change. A version that is not known has no `updatedAt` or `updatedBy` either: the line where it went missing is not an update. The row's outcome says only what was measured - a failed command names its exit code and still compares the versions before and after (it can have moved them), and a preset that declares no update command says nothing was run. The update button stays `HumansOnly` and goes through `AgentUpdateGate`. Pinned by `AgentCliVersionRouteTests.A_person_reads_each_presets_version_when_it_changed_and_who_brought_it`, `AgentCliVersionRouteTests.The_update_route_answers_with_the_entry_after_its_own_line_and_records_the_person`, `AgentCliVersionRouteTests.A_version_that_is_not_known_has_no_update_time_and_no_one_who_brought_it` and the web mount tests in `agents-dialog-versions.mount.spec.ts`.

A person's update is asked for, never awaited. `POST /api/agents/{name}/update` answers 202 at once with the state `AgentUpdateGate` holds (`AgentUpdateGate.Request`), and `GET` on the same path reads it back, so no request stays open for minutes and closing the dialog or reloading cancels nothing: reopening reads the same state. The state is the gate's, never estimated: `waiting` with `running` and `inFlight` naming the team and member of each run it waits for (as `/api/wip` names a slot's holder) and `held` naming each launch it holds, `updating` from the moment the last of those runs leaves (drawn under the gate's lock, so it never reads "waiting for 0 runs"), then the last one's outcome - `done` with its measured `result`, `cancelled`, or `failed` with its sentence - kept until the Host restarts. The row reads "Waiting for N <command> runs to finish: team / member, ...", "Updating…", then the outcome, polling while the update is in the gate. `DELETE` cancels an update only while it waits: it is removed, nothing runs, and the launches it held go ahead at once (`agent.update-cancelled`); a running update answers 409 with a sentence. One update per command at a time: asked again, the route answers the one in the gate. A launch held behind an update is held, never failed: it says "Waiting for the <command> update" once as its progress, and its kanban card carries "waiting for the <command> update" from `GET /api/agents/updates`. The update route, its read, its cancel and that list are all `HumansOnly`. Pinned by `AgentUpdatesTests.A_persons_update_asked_while_a_run_is_in_flight_answers_at_once_names_that_run_then_updates_then_says_its_outcome`, `AgentUpdatesTests.Cancelling_a_waiting_update_removes_it_and_releases_the_launches_it_held`, `AgentCliVersionRouteTests.An_update_asked_while_a_run_is_in_flight_answers_at_once_waiting_on_that_run_and_reads_the_same_when_the_dialog_reopens`, `AgentCliVersionRouteTests.A_running_update_cannot_be_cancelled` and the web mount tests in `agents-dialog-update-waiting.mount.spec.ts`.

## Identity

- The code says **Harness**. The product name is **Yawble** and, in code, it appears in exactly two files: `web/src/presentation/product.ts` and the `productName` in `web/package.json`, so renaming the product edits those and nothing that carries identifiers. Pinned by `BrandLeakTests.Brand_strings_stay_out_of_the_code` and `BrandLeakTests.The_brand_lives_in_the_presentation_layer`. The GitHub repository is `djlsystems/Yawble`. The one exception is `cli/`, the operator CLI: its binary is `yawble`, so the brand is its name, and `BrandLeakTests` skips `cli/` by path. The CLI shares this repository's tag, GitHub Release and version number (`v<yyyy.mm.dd.N>`, cut by `scripts/release.ps1` for image and binary together); there is no separate CLI repository. Not pinned: one tag for both is the release script's arithmetic, which `scripts/tests/release-functions.tests.ps1` checks offline, not a behaviour either suite runs.
- Environment variables use the `HARNESS_` prefix. A catalog or team env entry that sets one is dropped, not overwritten: a hand-edited file must not be able to hand a member another principal's credential. Pinned by `AgentEnvironmentTests.Harness_entries_in_a_catalog_or_team_env_are_dropped`.
- A headless child receives only its own provider's key (the command's `credentialVariable` in `auth-probes.json`), plus `GH_TOKEN` when its team has a GitHub remote. Every other provider key, and `GITHUB_TOKEN`, is REMOVED at the spawn site by `AgentEnvironment.ScopeProviderKeys`, not set empty; a key handed in explicitly (a catalog entry's own env, a team env entry) is kept. Pinned by `AgentEnvironmentTests.A_child_receives_only_its_own_provider_key`, `AgentEnvironmentTests.A_team_with_a_GitHub_remote_hands_its_member_GH_TOKEN_and_no_other_foreign_key` and `AgentEnvironmentTests.Copilot_keeps_GH_TOKEN_and_loses_every_other_provider_key`. The Host's own git follows the same rule: `GH_TOKEN` only for an operation on a GitHub team's remote, and a remote given by NAME (`ls-remote origin`, the `repo` refresh) is judged by the team's remotes, not by its spelling, or GitHub refuses the check while Fetch works. Pinned by `LsRemoteTokenTests`. **Not true for the Concierge:** its PTY path merges into the Host's environment and cannot remove a variable (see `AgentEnvironment.MustBeAbsent`), so it still inherits every provider key. **The Concierge also keeps every tool** (B001K): it is the person's own session, so it launches with the signed-in account's connectors (Claude's `claude_ai_*`), the shared home's MCP servers, plugins and skills, exactly as before. That is an accepted risk, like its provider keys: text the Concierge reads (a document, a team's output, a README) can ask it to use the person's accounts. A member never gets these tools, even when the Concierge tells it to do something; see Agents.
- The team marker is `.harness-team`. Deletion removes a directory only when that marker says this platform created it. Pinned by `TeamMarkerTests.A_team_root_carrying_the_marker_is_removed` and `TeamMarkerTests.A_team_root_without_the_marker_is_left_and_named`.
- A team root, a member's workspace and a folder Reset empties are removed one way, `FolderRemoval`, never `Directory.Delete(recursive: true)`: agents create owner-only directories the Host cannot empty, and a recursive delete took the marker first and then failed. The root is emptied around its marker, then the marker goes, then the root; anything left keeps the marker. When the Host switches users (`AgentLaunchUser`), what it cannot remove is removed as the agent with `rm -rf --one-file-system` through the existing launch prefix (no new privilege), only for paths that resolve inside the folder with no symbolic link on the way; links are removed as links and never followed; with no switch there is no agent pass. Whatever still remains is named path by path in the result (`remaining`), the delete dialog and the tenant log row, and recorded in `unfinished_removals` (`auth-012`); the Host retries every row at start, a person retries from the delete dialog or from the Teams view's list of every unfinished removal - team root, workspace and emptied folder, each with its remaining paths (`GET /api/removals`, `POST /api/removals/retry`), and creating a team over the unfinished removal of a deleted team of the same id finishes it first. A root without its marker is still never deleted, and a folder with no marker is still refused at creation. A retry of a Reset's folder removes only what the Reset named, never what was written since: a named file or link goes only when it was not modified after the row's first `recorded_at` (a link judged as itself, never its target), and one modified since is the member's, kept and no longer counted; a named directory loses only the entries in which nothing was modified after that time, and goes itself only once empty; once a named path is gone, the empty directories above it go too, up to but never including the folder, stopping at a link or a directory modified since, as best-effort clean-up by the Host (one it cannot remove is left in place and never keeps the row unfinished); a retry that takes more than one attempt still clears them: each unfinished attempt records the modification time its own deletes left on every directory it judged unwritten (`unfinished_removals.host_left`, `auth-013`), and a directory still at exactly that time is judged unwritten again, while one written in since has another time and is kept; a named directory the Host still cannot list (the folder itself included) stays unfinished and is never reported finished. Known residual risks: age is the modification time (a file copied in since with its old time kept counts as old), and the Host's pass resolves a directory by path after checking it is not a link, so an agent swapping it for a link in between could redirect the Host's deletes (closing that needs `openat`/`O_NOFOLLOW` deletes). Pinned by `FolderRemovalTests` (every case, marker-last, symlink, `MemberDeletion`, `TeamReset`, create over unfinished vs unmarked, and a Reset retry: `A_reset_retry_keeps_what_the_member_wrote_since_into_a_directory_the_reset_named`, `A_reset_retry_of_a_folder_it_could_not_list_stays_unfinished_until_it_can_be_emptied`, `A_reset_retry_keeps_a_named_file_the_member_rewrote_since_and_judges_a_named_link_by_itself`, `A_finished_reset_retry_removes_the_empty_directories_above_what_the_reset_named`, `A_reset_retry_that_took_two_attempts_removes_the_empty_directories_above_what_the_reset_named`, `A_reset_retry_that_took_two_attempts_keeps_a_directory_written_in_between_them`, `An_empty_directory_above_a_named_path_the_host_cannot_remove_is_left_and_the_reset_retry_finishes`), `UnfinishedRemovalHostTests.A_removal_that_failed_is_named_in_the_result_and_the_log_and_finished_at_the_next_start`, `UnfinishedRemovalHostTests.A_person_can_retry_a_removal_on_request` and `FolderRemovalAsTheAgentTests.An_agent_owned_owner_only_directory_with_files_in_it_is_removed_completely` (a real switch to `nobody`, skipped with the reason where the test process cannot switch). The web list is pinned by `web/src/components/__tests__/teams-view.mount.spec.ts` ("the unfinished removals list").
- A recursive delete (`Directory.Delete(x, true)`, `recursive: true`, `DirectoryInfo.Delete(true)`) is allowed in `src/` only where agents cannot write inside the folder: when the Host switches users, no process running as `agent` can create an entry anywhere in it. Anywhere they can - a team root and everything in it, a workspace, the documents, the sites folder, any other top-level data entry `prepare-volume.sh` gives to `agent`, anything shared to the agent with write - goes through `FolderRemoval` (`RemoveInsideAsync`, or `RemoveInsideOrThrowAsync` where the old delete threw, bounded so a link on the way is refused). So `SiteService` removes its version and site folders, and `SolutionInstaller` its tools, staging and plugin-version folders, through `FolderRemoval`. The reviewed exceptions, each with `// RECURSIVE DELETE REVIEWED: agents cannot write here. <why>` at the call: `McpLaunchConfig.Delete` and `CliListingRunner`'s scratch folder (Host-made owner-only folders `AgentLaunchUser.Share` opens to the agent's group for read and traverse, never write), `PluginInstaller` and `PluginRemover` (inside the plugins folder, harness:agent 0750, no group write), and `LocalRepos.RemoveQuietly` (a failed create's `.creating-` folder, made by the Host as itself inside the repos folder, harness:agent 2750, no group write; never a repository a team could clone). Pinned by `RecursiveDeleteInvariantTests.Every_recursive_delete_in_src_is_reviewed_and_says_why_agents_cannot_write_there`, which scans `src/` and fails on a recursive delete not on its `Reviewed` list (file and reason, one entry per call) or one without the comment, saying what to do; `RecursiveDeleteInvariantTests.The_scan_finds_every_spelling_of_a_recursive_delete_and_nothing_else` pins the scan.
- The cookie name comes from `InstanceIdentity`, a SHA-256 of the data root. `string.GetHashCode` is randomised per process and signs everyone out on every restart. Pinned by `IdentityTests.Cookie_name_is_stable_across_calls`.
- Data Protection keys live in `<dataRoot>/keys`. On Linux there is no DPAPI. The container boundary is the isolation. Do not copy the key directory into a member workspace. When the Host launches children as the separate `agent` user (see `AgentLaunchUser`), they cannot read the key directory, because it is the Host's own. When the Host cannot switch users (dev, tests, an image with no `agent` user), children run as the Host's user and CAN read the keys; that is stated here so nobody "fixes" it by pretending otherwise. The location is pinned by `DataProtectionKeysTests.Keys_are_written_under_the_data_root`. The rest is not pinnable here: nothing copies the key directory today, so a test would assert the absence of a feature, and who can read it depends on the image's owners and modes, not on the code.

## Data

- One data root, one database, one process. `--DataRoot` wins, then `HARNESS_DATA_ROOT`; with neither set the Host refuses to start. Pinned by `DataRootTests.The_setting_wins_over_the_environment_variable` and `DataRootTests.With_neither_set_the_host_refuses_to_start`. The container always sets `HARNESS_DATA_ROOT=/data`, which is a Podman volume; that is the `Containerfile` and the `podman run` line, outside what the test suites run, so it is not pinned.
- The schema migrator must be handed a **superset** of every step it has ever applied. Deleting a step makes a database that already applied it look corrupt. Pinned by `SchemaTests.Every_schema_step_applies_to_an_empty_database` and `SchemaTests.The_migrator_refuses_a_database_holding_a_step_it_was_not_handed`.
- The schema starts from one base step per store (`auth-001`, `messages-001`, `skill-001`, `backlog-001`). A change is a NEW step after those (`backlog-002` is B0025's recorded tips and stored landed; `backlog-003` is B0022's outcome on a backlog item, `backlog-004` is B0028's unrecorded starts); never edit one that has shipped. A volume whose recorded steps are not a subset of the known steps is refused and left alone. Pinned by `ShippedSchemaStepsTests.A_shipped_step_is_never_edited` (each shipped step's SQL is held to its SHA-256; a new step adds a line there), `ShippedSchemaStepsTests.Every_pinned_step_is_still_handed_to_the_migrator`, `FreshVolumeTests.The_steps_are_the_squash_and_the_steps_added_after_it` and `FreshVolumeTests.A_volume_from_before_the_squash_is_refused_and_left_alone`.
- A backlog item's stored key is its citation (`B001F`), minted from `backlog_id_sequence` and never reused. The contract and the route still carry the number; `SqliteBacklogStore` converts at the boundary. Pinned by `FreshVolumeTests.A_backlog_item_is_stored_under_its_citation_and_an_id_is_never_reused`.
- Documents survive team deletion and are listed and readable afterwards; a same-name recreation retires the old folder rather than handing it to the successor. Pinned by `DocumentsRetentionTests.Documents_survive_team_deletion_and_are_listed_and_readable_afterwards` and `DocumentsRetentionTests.A_same_name_team_recreation_retires_the_old_folder`.
- A person may delete any document, a non-empty folder only with `recursive=true` (409 without it), and a gone team's or retired folder's files, folders and whole folder; the whole folder only when its `.harness-team` marker names its team, and never a live team's. Upload and New folder still refuse a gone team. Every delete appends `documents.deleted` to `tenant_events` first, and does not happen when that row cannot be written; a recursive delete in a live team's folder announces each removed file to `FolderWatch`, one announcement per folder. Pinned by `DocumentsDeleteTests` (every case) and `DocumentsDeleteUnrecordedTests.Nothing_is_deleted_when_the_documents_deleted_row_cannot_be_written`; the dialog side by `web/src/components/__tests__/documents-dialog.mount.spec.ts`.
- A site is published by copying a folder the team may write (its documents folder or its team folder) into `<dataRoot>/sites/<team>/<site>/v<n>`, never linking to it, and the live version is the database's: it changes only after the copy is complete, in one transaction with its `site.published` tenant row, so an agent editing its working copy never changes what a person sees. Links and dot-names are not copied. The last five versions are kept; rollback makes a kept one live, unpublish keeps files and data, delete asks first (409 naming what is lost) and a team deletion removes its sites, their files and their data. Every site change (`site.created`, `site.published`, `site.rolled-back`, `site.unpublished`, `site.deleted`) appends its `tenant_events` row in the same transaction (`SqliteSiteStore`, `TenantAuditRow`); data writes are recorded on the document (`updated_at`, `updated_by`). Data limits - 64 KB a document, 10 000 documents a collection, 50 MB a site - and action limits - a 16 KB payload, a slug name - are refused with a sentence, the data limits checked inside the writing transaction. A member or plugin is a `SiteActor` bound to its own team, and another team's site answers what a missing one does. Pinned by `SitesTests.Publishing_changes_the_live_site_only_once_the_copy_is_complete_and_rollback_restores_the_previous`, `SitesTests.Deleting_a_site_asks_first_and_a_team_deletion_removes_its_sites_and_data`, `SitesTests.Each_limit_is_refused_with_a_sentence` and `SitesTests.A_member_bound_to_another_team_is_refused_as_if_the_site_did_not_exist`.
- A site action is ONE `site.action` row on the team's log, source `site:<team>/<site>`, NO causation (it roots a workflow, as a trigger's fire does), payload `{team, site, action, siteAction, payload, by, at}` with `by` the person's email; `MessageTeam` reads its `team`, which only the action route writes. `EventCatalog` knows the type, not high volume. An event trigger narrows it with `site eq <site>` or `siteAction eq <site>/<action>`, and its fire joins the action's workflow. Pinned by `SitesTests.A_site_action_is_one_event_row_rooting_a_new_workflow` and `SiteActionTriggerTests.A_trigger_narrowed_to_a_site_and_optionally_an_action_fires_on_those_only`.
- A cursor is **removed**, never zeroed. Zeroing it lets retention get stuck behind it. Pinned by `CursorRemovalTests.A_forgotten_cursor_no_longer_holds_retention_back` and `CursorRemovalTests.Forgetting_the_last_cursor_leaves_no_position_rather_than_zero`.
- A team repository's default branch is stored, never assumed. `auth-006` keeps two columns per repository in `team_repo_default_branches`: `from_remote`, what `git remote set-head origin --auto` read on the last clone or successful Fetch (NULL when that read fails or HEAD names no branch), and `set_by_person`, a choice from Team settings that no Fetch touches and that wins until cleared. No row, or NULL in both, is not known: every Git action that needs the branch (bring current, rebase, push, merge to main, delete the team branch, ask the team, landed) answers 409 or `unknown` and changes nothing, and the publisher never pushes it. A failed Fetch leaves a stored value, or not known, as it was. Nothing backfills `main`, and the clone folder stays `repos/<Repo>/main`. At start, a clone whose `from_remote` is NULL is read once from the `refs/remotes/origin/HEAD` it already holds, with no network (`DefaultBranchAtStart`), so an existing clone is not left not known until a person presses Fetch; a clone with no such ref stays not known. Pinned by `DefaultBranchAtStartTests.A_clone_with_no_stored_branch_is_read_at_the_next_start`. `set-head --auto` asks origin, so it gets `GH_TOKEN` by the team's remotes as a fetch does; without it a private repository refuses the read and every Fetch would write not known over the stored branch. Pinned by `LsRemoteTokenTests.The_default_branch_read_of_a_GitHub_teams_origin_is_handed_the_token`. Pinned by `RepoDefaultBranchTests`, `FreshVolumeTests.A_repository_from_before_the_default_branch_step_is_not_known_afterwards` and `PublisherRejectionTests.The_stored_default_branch_is_never_published`; the web side by `repoStatus.spec.ts`, `repoLadder.spec.ts` ("the stored default branch") and `team-settings-default-branch.mount.spec.ts`.
- Contributor mode is per repository. `auth-007` keeps a row in `team_repo_contributors` per repository: an optional `upstream_url` (set: the repository's own URL is the fork, `origin`), `fork_owner`, `dco_sign_off`, `cla_signed_note` and the recorded pull request (URL, number, state, read-at). The clone gets an `upstream` remote beside origin; setting or clearing the upstream adds, re-points or removes that remote and nothing else, and a clone made later gets it when it is made. Fetch fetches both; Bring current and Rebase use `upstream/<default>` and still stop when the default branch is not known. Bring current also syncs the fork - `git push origin upstream/<default>:refs/heads/<default>`, never forced, the ONE push of a default branch the platform makes and only from upstream - and refuses a fork whose `<default>` has commits upstream lacks, naming the count and changing nothing. `repo.forkSynced` is appended after that push. "Sign off commits (DCO)" writes a marked `commit-msg` hook into the clone's `.git/hooks` (worktrees share it) using `git interpret-trailers --if-exists doNothing` with the instance's `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`; turning it on without them is refused naming the fix (the operator CLI's `secret set GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL`), and a hook the platform did not write is never replaced or removed. Agents get no new tool, skill text or environment, and never push, fork or open a pull request. Pinned by `ContributorModeTests`, `FreshVolumeTests.A_repository_from_before_the_contributor_step_is_owned_afterwards`; the web side by `contributor.spec.ts`, `team-settings-contributor.mount.spec.ts`, `create-team-dialog.mount.spec.ts` and `repo-card-states.mount.spec.ts`.
- Contributor mode's GitHub buttons are a person's only: Merge to main answers 409 in contributor mode and the Git dialog offers Open pull request instead (`gh pr create --repo <upstream> --head <fork-owner>:team/{id} --base <default>`, title and body edited first), refused while the default branch is not known, while team/{id} is not on the fork, and - DCO on - while any commit since `upstream/<default>` lacks Signed-off-by, naming them; an open one is linked, never doubled; `repo.pullRequestOpened` is appended after GitHub opened it. Fork it for me is `POST /api/github/fork` (`gh repo fork --clone=false`, `--org` only when given). Landed in contributor mode is the recorded pull request's state (`in-review`, `declined`, `landed`; unreachable or refused is `unknown`), asked when the backlog or Git dialog is read and at most once a minute per pull request (`PullRequestStateReader`). GitHub is reached only through `IGitHubContributor`; tests fake it and never call GitHub. The operator CLI's `github` and `doctor` say contributor mode needs a classic token with `public_repo` (`repo` for a private upstream). Pinned by `PullRequestTests`; the web side by `repoLadder.spec.ts`, `repo-card-states.mount.spec.ts`, `backlog.spec.ts` and `fork-it-for-me.mount.spec.ts`.
- A backlog item's `landed` is claimed only from positive evidence (ancestry from `origin/<default>` by the stored default branch, or in contributor mode a merged pull request), and once proven it is stored and kept (B0025). `backlog-002` records per dispatch and repository the team branch's tip (`backlog_dispatch_tips`: repository name, never the URL; sha; recorded_at), written when the team's publish pushes `team/<id>` and replaced by each newer publish (`TeamPublisher` → `BacklogTipRecorder`; none for a contributor-mode repository), and adds `landed_at`, `landed_sha` and `landed_branch` to `backlog_dispatches`. ## Authorization

- Every human login sees every team. Per-team grants are not an authorization axis and there is no grants table: `auth-001` does not create one. `TeamGate` passes a person straight to the handler, which answers 404 for a team that does not exist; a machine principal is refused a team that is not its own, with the same body a missing team gets. ## Outcomes

An outcome names the business result a workflow serves. `outcomes` and the append-only `workflow_outcome_links` are `outcome-002`, in the log's database file; `triggers.outcome_id` is `auth-017` and `backlog_items.outcome_id` is `backlog-003`; `workflow_ledger.outcome_id_at_close` is the newest link's outcome when the workflow closed. A workflow's outcome is its newest link, followed through `merged_into`. Links are made at the root: a backlog dispatch's `backlog.item.dispatched` row and a trigger's or schedule's fire link from `SqliteMessageStore`'s one insert (`OutcomeLinks.OnAppendAsync`), in the same transaction as that row, attributed to the dispatching person (`how: dispatch`) or the trigger's configurer (`how: trigger`) and never over an existing link; a `tell` without causation that names `outcome` (an id, or the exact name of an active or proposed outcome) links in its append's transaction (`how: tell`). A solution package's trigger may name an outcome by name, and the install creates it `active`. The `outcome` tool (list, show, set, propose) is the Manager's and the Concierge's; `set` and `propose` resolve the workflow as `tell` resolves causation. `outcomes.requireForCompletion` is off by default. A kanban card carries `outcome` (id, name, status): its open workflow's, else its latest workflow's, attached by `CardOutcomes.AttachAsync` after `CardOpenWorkflows.AttachAsync` in ONE query per board read (`IOutcomeStore.CurrentOutcomesAsync`); the board's `outcome` filter (`KanbanFilter.Outcome`, an id or `none`) matches that tag, and the team workflows route stamps the same on each row. In the web, the card's tag is text, dashed with "proposed" for a proposed outcome and absent for none, and clicking it emits `open-outcome` with the id; pinned by `kanban-outcomes.mount.spec.ts`, `outcome-pickers.mount.spec.ts` and the Outcome column case in `team-kpi-workflow-actions.mount.spec.ts`. Every person's write appends its `tenant_events` row in the same transaction and does not happen when that row cannot be written; a Manager's propose and set append rows naming the member. `GET /api/outcomes/{id}` answers its `events` from those rows (`outcome.*` whose subject is the outcome or one merged into it, oldest first, each with `by` and `at`), so its history needs nothing recorded twice. Figures come from the ledger: agent time is summed, elapsed is median and longest and never summed, an unmeasured run is counted and never zero, a deleted team is named from its snapshot, and unlinked workflows are "No outcome". ## Solution packages

- A **solution package** (`solution.json` format 1, `docs/solutions.md`) is read only through `SolutionService` and `SolutionChecker`: the check route, the operator's `--solution-check`, the install, the update and the preview all take the same parsed `SolutionPackage`, and none reads the folder a second way. Unknown top-level keys are kept and listed as `ignored`, never refused, so a package written for a later Host still checks. It refuses a trigger naming a member the package lacks, a plugin member naming a plugin it does not ship, a skill named like a built-in (or `plugin-`), an event type the catalog does not know, and any path or link escaping the package or the team's documents. `POST /api/solutions/check` carries one marker, `RequirePermit(CreateTeam)` (the Concierge's, never a team's), and its handler refuses a member besides. ## Admission

- `wip.maxRunning` (a tenant setting, falling back to `Wip:MaxRunning`) is instance-wide and shared across users. Default: the smaller of the CPU bound `max(1, cgroup CPUs - 1)` (3 when the CPUs are not known) and, when the container has a memory limit (`/sys/fs/cgroup/memory.max`), the memory bound `floor(limit / wip.memoryPerRunMb)`, at least 1; `wip.memoryPerRunMb` is a tenant setting, default 2048 (`Wip:MemoryPerRunMb`). The default is computed on read (`TenantSettings.RunLimit`), so a change to the allowance moves it without a restart and `Program.cs` re-applies the ledger's limit on either change. ## Containment

- A run's own memory limit is applied from inside the container, never by asking the engine. `RunMemoryLimits` is decided once at start and logged ("Run memory limits: cgroup | rlimit | not available — <reason>", followed by the limit each run now gets), the way `AgentLaunchUser` logs its decision. The decision takes the best mechanism available. **cgroup** needs cgroup v2, the memory controller delegated, and the Host's own cgroup writable (probed by making and removing a child); each run then gets its own `run-<id>` child with `memory.max`, `memory.oom.group` and no swap, and `oom_kill` in its `memory.events` is what says the limit stopped it. Otherwise **rlimit**: `prlimit` from a root-owned system directory, with `--data=N:N` placed AFTER the `AgentLaunchUser` prefix, so it runs with no capability and the agent cannot raise the hard limit. It is per process, not the run's total, and the log line says so. Otherwise **not available**, said plainly. The limit is the tenant setting `runs.memoryLimitMb`, read through a delegate at every launch: 0 (default) is (container limit - `TenantSettings.HostReserveMb`) / `wip.maxRunning`, at least `MinRunMemoryLimitMb`, and none with no container limit. ## Reset repositories

- **Reset repositories never forces, and never loses what only a person could decide to lose.** It is a team-wide box on the reset dialog, off by default (`TeamResetOptions.ResetRepositories`), and the dialog lists what is lost before the person confirms: each ticked member's worktrees and branches, and the team branch `team/<id>` when every member is ticked (`GET /api/teams/{team}/reset/repositories`, `.HumansOnly()`, reads only). - **The team branch is reset only with every member ticked, and only to the STORED default branch.** Not known refuses the whole reset with `DefaultBranchNotKnown`'s sentence (409) before anything moves, so nothing else changes. In the clone `team/<id>` is moved to the default branch (the local one, else `origin/<default>`) unless it holds a commit on no remote and not on the default branch, is checked out in a kept tree, or is checked out in a clone with uncommitted edits; each of those keeps it, named (`repositories.teamBranchKept`). ## Tests

- A test that was not seen to fail for the right reason does not prove the fix.
- A mock in the wrong shape is a confident test. Thirteen green cases while the feature 404s is the failure mode.
- These two are rules for writing tests, so no test can pin them.
- A test Host never starts a real agent. The release runs the suite inside the product image, where the agent CLIs are installed and signed in, and a test that fires a trigger or tells a member would otherwise start a real, paid run with the signed-in account's tools, which outlives its test Host. `AgentCliIsolation` puts a stub of every built-in language-model preset's command (not `bash` or `cat`, which call no model) first on the test process's PATH at load; the stub says why and exits 1. A test that wants a real program names its own command. Pinned by `AgentCliIsolationTests.Every_built_in_presets_command_resolves_to_the_stub_for_this_test_process` and `AgentCliIsolationTests.The_stub_says_why_and_fails_without_starting_anything`.
- `dotnet test` on this repo's Microsoft.Testing.Platform projects can report "zero tests" even when the assembly has tests. Run the test dll directly: `dotnet tests/Harness.Tests/bin/Debug/net10.0/Harness.Tests.dll` after a build. This describes the tooling, so it is not pinned.
- A rule above that names no test has none. A rule marked **Currently VIOLATED** is pinned by a Skipped test that fails when un-skipped; the fix removes the Skip. A rule that cannot be pinned says so, and why.
