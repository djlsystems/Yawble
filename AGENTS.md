# Yawble core: contributor rules

For people and coding agents working on this repository. Rules that are load-bearing, and the failure each one prevents. Most name the test that pins them; keep that test green and keep the rule true when you change the code. For what the product is and how to build it, see `README.md` and `docs/architecture.md`.

The Host runs in a Linux container. An agent child starts in its own session (`setsid`), and its process group is killed when the run ends, so a detached grandchild does not outlive it. A command is resolved with `PathSearch.Find`, and a miss is a launch failure once the launch has looked again for about 30 seconds. The launch lives in `ChildProcess`, which agent and plugin members share. Pinned by `ChildProcessTests`, `ProcessAgentRunnerLaunchTests.The_child_leads_its_own_process_group`, `ProcessAgentRunnerLaunchTests.A_detached_grandchild_does_not_outlive_the_run`, `ProcessAgentRunnerLaunchTests.A_command_not_on_PATH_is_a_launch_failure` and `PathSearchTests.A_missing_command_is_null`.

A program missing at launch is not an agent fault. The shared install every member launches from is replaced in place while a CLI updates, so a launch can find no program for a few seconds. `ChildProcess.FindAsync` looks again every few seconds for about 30 (`LaunchLookup`, injectable so tests do not wait), and a program that appears is launched as normal with nothing recorded but one progress line. One that never appears fails with the class `launch-missing`, whose words say the program was not found when the run started, may be being installed or updated, and that re-sending the instruction will try again; they ask nobody to repair anything. The Manager prompt and skill say such a failure is re-sent, and escalated to a person only when it has already happened twice. Pinned by `LaunchMissingTests.A_program_missing_at_launch_that_appears_two_seconds_later_starts_the_run_normally`, `LaunchMissingTests.A_program_that_never_appears_fails_launch_missing_and_is_not_an_agent_fault` and `LaunchMissingTests.The_Managers_context_for_a_launch_missing_failure_says_re_send_and_names_nobody_to_repair_anything`.

## Identity

- The code says **Harness**. The product name is **Yawble** and, in code, it appears in exactly two files: `web/src/presentation/product.ts` and the `productName` in `web/package.json`, so renaming the product edits those and nothing that carries identifiers. Pinned by `BrandLeakTests.Brand_strings_stay_out_of_the_code` and `BrandLeakTests.The_brand_lives_in_the_presentation_layer`. The GitHub repository is `djlsystems/Yawble`. The one exception is `cli/`, the operator CLI: its binary is `yawble`, so the brand is its name, and `BrandLeakTests` skips `cli/` by path. The CLI shares this repository's tag, GitHub Release and version number (`v<yyyy.mm.dd.N>`, cut by `scripts/release.ps1` for image and binary together); there is no separate CLI repository. Not pinned: one tag for both is the release script's arithmetic, which `scripts/tests/release-functions.tests.ps1` checks offline, not a behaviour either suite runs.
- Environment variables use the `HARNESS_` prefix. A catalog or team env entry that sets one is dropped, not overwritten: a hand-edited file must not be able to hand a member another principal's credential. Pinned by `AgentEnvironmentTests.Harness_entries_in_a_catalog_or_team_env_are_dropped`.
- A headless child receives only its own provider's key (the command's `credentialVariable` in `auth-probes.json`), plus `GH_TOKEN` when its team has a GitHub remote. Every other provider key, and `GITHUB_TOKEN`, is REMOVED at the spawn site by `AgentEnvironment.ScopeProviderKeys`, not set empty; a key handed in explicitly (a catalog entry's own env, a team env entry) is kept. Pinned by `AgentEnvironmentTests.A_child_receives_only_its_own_provider_key`, `AgentEnvironmentTests.A_team_with_a_GitHub_remote_hands_its_member_GH_TOKEN_and_no_other_foreign_key` and `AgentEnvironmentTests.Copilot_keeps_GH_TOKEN_and_loses_every_other_provider_key`. The Host's own git follows the same rule: `GH_TOKEN` only for an operation on a GitHub team's remote, and a remote given by NAME (`ls-remote origin`, the `repo` refresh) is judged by the team's remotes, not by its spelling, or GitHub refuses the check while Fetch works. Pinned by `LsRemoteTokenTests`. **Not true for the Concierge:** its PTY path merges into the Host's environment and cannot remove a variable (see `AgentEnvironment.MustBeAbsent`), so it still inherits every provider key.
- The team marker is `.harness-team`. Deletion removes a directory only when that marker says this platform created it. Pinned by `TeamMarkerTests.A_team_root_carrying_the_marker_is_removed` and `TeamMarkerTests.A_team_root_without_the_marker_is_left_and_named`.
- A team root, a member's workspace and a folder Reset empties are removed one way, `FolderRemoval`, never `Directory.Delete(recursive: true)`: agents create owner-only directories the Host cannot empty, and a recursive delete took the marker first and then failed. The root is emptied around its marker, then the marker goes, then the root; anything left keeps the marker. When the Host switches users (`AgentLaunchUser`), what it cannot remove is removed as the agent with `rm -rf --one-file-system` through the existing launch prefix (no new privilege), only for paths that resolve inside the folder with no symbolic link on the way; links are removed as links and never followed; with no switch there is no agent pass. Whatever still remains is named path by path in the result (`remaining`), the delete dialog and the tenant log row, and recorded in `unfinished_removals` (`auth-012`); the Host retries every row at start, a person retries from the delete dialog or from the Teams view's list of every unfinished removal - team root, workspace and emptied folder, each with its remaining paths (`GET /api/removals`, `POST /api/removals/retry`), and creating a team over the unfinished removal of a deleted team of the same id finishes it first. A root without its marker is still never deleted, and a folder with no marker is still refused at creation. A retry of a Reset's folder removes only what the Reset named, never what was written since: a named file or link goes only when it was not modified after the row's first `recorded_at` (a link judged as itself, never its target), and one modified since is the member's, kept and no longer counted; a named directory loses only the entries in which nothing was modified after that time, and goes itself only once empty; once a named path is gone, the empty directories above it go too, up to but never including the folder, stopping at a link or a directory modified since, as best-effort clean-up by the Host (one it cannot remove is left in place and never keeps the row unfinished); a retry that takes more than one attempt still clears them: each unfinished attempt records the modification time its own deletes left on every directory it judged unwritten (`unfinished_removals.host_left`, `auth-013`), and a directory still at exactly that time is judged unwritten again, while one written in since has another time and is kept; a named directory the Host still cannot list (the folder itself included) stays unfinished and is never reported finished. Known residual risks: age is the modification time (a file copied in since with its old time kept counts as old), and the Host's pass resolves a directory by path after checking it is not a link, so an agent swapping it for a link in between could redirect the Host's deletes (closing that needs `openat`/`O_NOFOLLOW` deletes). Pinned by `FolderRemovalTests` (every case, marker-last, symlink, `MemberDeletion`, `TeamReset`, create over unfinished vs unmarked, and a Reset retry: `A_reset_retry_keeps_what_the_member_wrote_since_into_a_directory_the_reset_named`, `A_reset_retry_of_a_folder_it_could_not_list_stays_unfinished_until_it_can_be_emptied`, `A_reset_retry_keeps_a_named_file_the_member_rewrote_since_and_judges_a_named_link_by_itself`, `A_finished_reset_retry_removes_the_empty_directories_above_what_the_reset_named`, `A_reset_retry_that_took_two_attempts_removes_the_empty_directories_above_what_the_reset_named`, `A_reset_retry_that_took_two_attempts_keeps_a_directory_written_in_between_them`, `An_empty_directory_above_a_named_path_the_host_cannot_remove_is_left_and_the_reset_retry_finishes`), `UnfinishedRemovalHostTests.A_removal_that_failed_is_named_in_the_result_and_the_log_and_finished_at_the_next_start`, `UnfinishedRemovalHostTests.A_person_can_retry_a_removal_on_request` and `FolderRemovalAsTheAgentTests.An_agent_owned_owner_only_directory_with_files_in_it_is_removed_completely` (a real switch to `nobody`, skipped with the reason where the test process cannot switch). The web list is pinned by `web/src/components/__tests__/teams-view.mount.spec.ts` ("the unfinished removals list").
- The cookie name comes from `InstanceIdentity`, a SHA-256 of the data root. `string.GetHashCode` is randomised per process and signs everyone out on every restart. Pinned by `IdentityTests.Cookie_name_is_stable_across_calls`.
- Data Protection keys live in `<dataRoot>/keys`. On Linux there is no DPAPI. The container boundary is the isolation. Do not copy the key directory into a member workspace. When the Host launches children as the separate `agent` user (see `AgentLaunchUser`), they cannot read the key directory, because it is the Host's own. When the Host cannot switch users (dev, tests, an image with no `agent` user), children run as the Host's user and CAN read the keys; that is stated here so nobody "fixes" it by pretending otherwise. The location is pinned by `DataProtectionKeysTests.Keys_are_written_under_the_data_root`. The rest is not pinnable here: nothing copies the key directory today, so a test would assert the absence of a feature, and who can read it depends on the image's owners and modes, not on the code.

## Data

- One data root, one database, one process. `--DataRoot` wins, then `HARNESS_DATA_ROOT`; with neither set the Host refuses to start. Pinned by `DataRootTests.The_setting_wins_over_the_environment_variable` and `DataRootTests.With_neither_set_the_host_refuses_to_start`. The container always sets `HARNESS_DATA_ROOT=/data`, which is a Podman volume; that is the `Containerfile` and the `podman run` line, outside what the test suites run, so it is not pinned.
- The schema migrator must be handed a **superset** of every step it has ever applied. Deleting a step makes a database that already applied it look corrupt. Pinned by `SchemaTests.Every_schema_step_applies_to_an_empty_database` and `SchemaTests.The_migrator_refuses_a_database_holding_a_step_it_was_not_handed`.
- The schema starts from one base step per store (`auth-001`, `messages-001`, `skill-001`, `backlog-001`). A change is a NEW step after those; never edit one that has shipped. A volume whose recorded steps are not a subset of the known steps is refused and left alone. Pinned by `ShippedSchemaStepsTests.A_shipped_step_is_never_edited` (each shipped step's SQL is held to its SHA-256; a new step adds a line there), `ShippedSchemaStepsTests.Every_pinned_step_is_still_handed_to_the_migrator`, `FreshVolumeTests.The_steps_are_the_squash_and_the_steps_added_after_it` and `FreshVolumeTests.A_volume_from_before_the_squash_is_refused_and_left_alone`.
- A backlog item's stored key is its citation (`B001F`), minted from `backlog_id_sequence` and never reused. The contract and the route still carry the number; `SqliteBacklogStore` converts at the boundary. Pinned by `FreshVolumeTests.A_backlog_item_is_stored_under_its_citation_and_an_id_is_never_reused`.
- Documents survive team deletion and are listed and readable afterwards; a same-name recreation retires the old folder rather than handing it to the successor. Pinned by `DocumentsRetentionTests.Documents_survive_team_deletion_and_are_listed_and_readable_afterwards` and `DocumentsRetentionTests.A_same_name_team_recreation_retires_the_old_folder`.
- A person may delete any document, a non-empty folder only with `recursive=true` (409 without it), and a gone team's or retired folder's files, folders and whole folder; the whole folder only when its `.harness-team` marker names its team, and never a live team's. Upload and New folder still refuse a gone team. Every delete appends `documents.deleted` to `tenant_events` first, and does not happen when that row cannot be written; a recursive delete in a live team's folder announces each removed file to `FolderWatch`, one announcement per folder. Pinned by `DocumentsDeleteTests` (every case) and `DocumentsDeleteUnrecordedTests.Nothing_is_deleted_when_the_documents_deleted_row_cannot_be_written`; the dialog side by `web/src/components/__tests__/documents-dialog.mount.spec.ts`.
- A site is published by copying a folder the team may write (its documents folder or its team folder) into `<dataRoot>/sites/<team>/<site>/v<n>`, never linking to it, and the live version is the database's: it changes only after the copy is complete, in one transaction with its `site.published` tenant row, so an agent editing its working copy never changes what a person sees. Links and dot-names are not copied. The last five versions are kept; rollback makes a kept one live, unpublish keeps files and data, delete asks first (409 naming what is lost) and a team deletion removes its sites, their files and their data. Every site change (`site.created`, `site.published`, `site.rolled-back`, `site.unpublished`, `site.deleted`) appends its `tenant_events` row in the same transaction (`SqliteSiteStore`, `TenantAuditRow`); data writes are recorded on the document (`updated_at`, `updated_by`). Data limits - 64 KB a document, 10 000 documents a collection, 50 MB a site - and action limits - a 16 KB payload, a slug name - are refused with a sentence, the data limits checked inside the writing transaction. A member or plugin is a `SiteActor` bound to its own team, and another team's site answers what a missing one does. Pinned by `SitesTests.Publishing_changes_the_live_site_only_once_the_copy_is_complete_and_rollback_restores_the_previous`, `SitesTests.Deleting_a_site_asks_first_and_a_team_deletion_removes_its_sites_and_data`, `SitesTests.Each_limit_is_refused_with_a_sentence` and `SitesTests.A_member_bound_to_another_team_is_refused_as_if_the_site_did_not_exist`.
- A site action is ONE `site.action` row on the team's log, source `site:<team>/<site>`, NO causation (it roots a workflow, as a trigger's fire does), payload `{team, site, action, siteAction, payload, by, at}` with `by` the person's email; `MessageTeam` reads its `team`, which only the action route writes. `EventCatalog` knows the type, not high volume. An event trigger narrows it with `site eq <site>` or `siteAction eq <site>/<action>`, and its fire joins the action's workflow. Pinned by `SitesTests.A_site_action_is_one_event_row_rooting_a_new_workflow` and `SiteActionTriggerTests.A_trigger_narrowed_to_a_site_and_optionally_an_action_fires_on_those_only`.
- A cursor is **removed**, never zeroed. Zeroing it lets retention get stuck behind it. Pinned by `CursorRemovalTests.A_forgotten_cursor_no_longer_holds_retention_back` and `CursorRemovalTests.Forgetting_the_last_cursor_leaves_no_position_rather_than_zero`.
- A team repository's default branch is stored, never assumed. `auth-006` keeps two columns per repository in `team_repo_default_branches`: `from_remote`, what `git remote set-head origin --auto` read on the last clone or successful Fetch (NULL when that read fails or HEAD names no branch), and `set_by_person`, a choice from Team settings that no Fetch touches and that wins until cleared. No row, or NULL in both, is not known: every Git action that needs the branch (bring current, rebase, push, merge to main, delete the team branch, ask the team, landed) answers 409 or `unknown` and changes nothing, and the publisher never pushes it. A failed Fetch leaves a stored value, or not known, as it was. Nothing backfills `main`, and the clone folder stays `repos/<Repo>/main`. At start, a clone whose `from_remote` is NULL is read once from the `refs/remotes/origin/HEAD` it already holds, with no network (`DefaultBranchAtStart`), so an existing clone is not left not known until a person presses Fetch; a clone with no such ref stays not known. Pinned by `DefaultBranchAtStartTests.A_clone_with_no_stored_branch_is_read_at_the_next_start`. `set-head --auto` asks origin, so it gets `GH_TOKEN` by the team's remotes as a fetch does; without it a private repository refuses the read and every Fetch would write not known over the stored branch. Pinned by `LsRemoteTokenTests.The_default_branch_read_of_a_GitHub_teams_origin_is_handed_the_token`. Pinned by `RepoDefaultBranchTests`, `FreshVolumeTests.A_repository_from_before_the_default_branch_step_is_not_known_afterwards` and `PublisherRejectionTests.The_stored_default_branch_is_never_published`; the web side by `repoStatus.spec.ts`, `repoLadder.spec.ts` ("the stored default branch") and `team-settings-default-branch.mount.spec.ts`.
- Contributor mode is per repository. `auth-007` keeps a row in `team_repo_contributors` per repository: an optional `upstream_url` (set: the repository's own URL is the fork, `origin`), `fork_owner`, `dco_sign_off`, `cla_signed_note` and the recorded pull request (URL, number, state, read-at). The clone gets an `upstream` remote beside origin; setting or clearing the upstream adds, re-points or removes that remote and nothing else, and a clone made later gets it when it is made. Fetch fetches both; Bring current and Rebase use `upstream/<default>` and still stop when the default branch is not known. Bring current also syncs the fork - `git push origin upstream/<default>:refs/heads/<default>`, never forced, the ONE push of a default branch the platform makes and only from upstream - and refuses a fork whose `<default>` has commits upstream lacks, naming the count and changing nothing. `repo.forkSynced` is appended after that push. "Sign off commits (DCO)" writes a marked `commit-msg` hook into the clone's `.git/hooks` (worktrees share it) using `git interpret-trailers --if-exists doNothing` with the instance's `GIT_AUTHOR_NAME`/`GIT_AUTHOR_EMAIL`; turning it on without them is refused naming the fix (the operator CLI's `secret set GIT_AUTHOR_NAME` / `GIT_AUTHOR_EMAIL`), and a hook the platform did not write is never replaced or removed. Agents get no new tool, skill text or environment, and never push, fork or open a pull request. Pinned by `ContributorModeTests`, `FreshVolumeTests.A_repository_from_before_the_contributor_step_is_owned_afterwards`; the web side by `contributor.spec.ts`, `team-settings-contributor.mount.spec.ts`, `create-team-dialog.mount.spec.ts` and `repo-card-states.mount.spec.ts`.
- Contributor mode's GitHub buttons are a person's only: Merge to main answers 409 in contributor mode and the Git dialog offers Open pull request instead (`gh pr create --repo <upstream> --head <fork-owner>:team/{id} --base <default>`, title and body edited first), refused while the default branch is not known, while team/{id} is not on the fork, and - DCO on - while any commit since `upstream/<default>` lacks Signed-off-by, naming them; an open one is linked, never doubled; `repo.pullRequestOpened` is appended after GitHub opened it. Landed in contributor mode is the recorded pull request's state (`in-review`, `declined`, `landed`; unreachable or refused is `unknown`), asked when the backlog or Git dialog is read and at most once a minute per pull request (`PullRequestStateReader`). GitHub is reached only through `IGitHubContributor`; tests fake it and never call GitHub. The operator CLI's `github` and `doctor` say contributor mode needs a classic token with `public_repo` (`repo` for a private upstream). Pinned by `PullRequestTests`; the web side by `repoLadder.spec.ts`, `repo-card-states.mount.spec.ts`, `backlog.spec.ts` and `fork-it-for-me.mount.spec.ts`.

## Authorization

- Every human login sees every team. Per-team grants are not an authorization axis and there is no grants table: `auth-001` does not create one. `TeamGate` passes a person straight to the handler, which answers 404 for a team that does not exist; a machine principal is refused a team that is not its own, with the same body a missing team gets. Pinned by `TeamGateTests.A_container_reaches_its_own_team`, `TeamGateTests.A_container_is_refused_another_team_with_the_body_a_missing_team_gets` and `TeamGateTests.A_person_on_a_missing_team_gets_the_handlers_404`.
- **Verb permits stay.** They bound machine principals. Collapsing "which team" and "which verb" is the change to refuse. A member credential must not perform tenant administration. Pinned by `PermitTests.A_container_key_is_refused_tenant_administration` and `PermitTests.A_person_may`.
- Every endpoint carries exactly one of `RequirePermit`, `NoPermitRequired` or `HumansOnly`. Pinned by `RouteMarkerTests.Every_endpoint_carries_exactly_one_marker`.
- `{team}` stays in the route. It tells the handler which team to act on. It is not an access-control key for humans. The second half is pinned by `CrossTeamTests.A_person_and_a_concierge_reach_every_team`. That the segment stays is a route-design decision with no behaviour of its own to assert, so it is not pinned.
- A container principal is bound to its own team. That is identity, not a grant. There is no tenant-scoped team. A person, a person's key and the tenant Concierge reach every team that exists. Pinned by `CrossTeamTests.A_container_reaches_its_own_team`, `CrossTeamTests.A_container_is_refused_another_teams_verb_with_what_a_missing_team_gets`, `CrossTeamTests.A_person_and_a_concierge_reach_every_team` and `CrossTeamTests.A_container_sees_only_its_own_team_in_the_overview`.

## The log

- The container subscribes, not the agent. The agent exits; the container holds the subscription. Pinned by `ContainerSubscriptionTests.A_container_whose_agent_has_exited_is_woken_by_the_next_instruction`.
- The ledger is a projection of the message log. Context comes from the ledger, not the transcript. Pinned by `LedgerContextTests.The_next_runs_context_holds_the_last_runs_output_and_not_its_progress`.

- A container does not react to its own publications, and it is woken only by its own team. A null team fails closed. - A Manager is woken **once per finished run**. It holds both `handback` and `completed`; a worker that handed back has already woken it, so its `completed` row carries `handedBack: true` and the pump passes a subscriber over on it when that subscriber also holds `handback`. - A **quiet** run wakes nobody on its completion. A plugin's result record may carry `quiet: true`. Its `completed` row is still written and shown, marked `quiet: true`, and the pump passes over every subscriber on that row, the same way it passes over a Manager on a `handedBack` row. A failure is never quiet. An event the run published, and a hand-back in it, wake on their own rows. Where a person sees runs it is marked too: `GET .../members/{member}/runs` carries `quiet` per run (true only for a quiet `completed` row). A run answering an instruction another member sent (its source is a member's id, as a Manager's `tell` is) is never quiet: that member is waiting, and a quiet row would leave it uninformed and its workflow open. Pinned by `PluginQuietRunTests.A_scheduled_plugin_run_that_finishes_quiet_wakes_nobody`, `PluginQuietRunTests.The_same_scheduled_run_not_quiet_wakes_the_manager_exactly_once`, `PluginQuietRunTests.A_quiet_run_that_publishes_an_event_still_wakes_the_events_trigger`, `PluginQuietRunTests.A_quiet_run_that_fails_still_wakes_the_manager`, `PluginQuietRunTests.The_runs_route_marks_a_quiet_run_quiet_and_a_loud_one_not` and `PluginHostProbes.A_quiet_answer_to_the_managers_own_instruction_still_wakes_the_manager`. - A **trigger decides whether its runs wake the Manager** (`triggers.wake_manager`, `auth-010`): `always`, `onHandbackOrFailure` (the default for a new trigger of every kind) or `never`; a trigger from before the step keeps `always`. The fire's instruction carries the choice as `wakeManager`, and the run's `completed` or `failed` row carries it on, as one key, only when it is not `always` (as `quiet` and `handedBack` ride on that row), so every other row is byte for byte what it was. A hand-back is its own row and still wakes. ## Usage

- Nothing is estimated. Unknown stays unknown. Pinned by `UnknownUsageTests.A_run_that_reports_no_usage_publishes_no_token_figures_and_is_counted_as_unmeasured` and `UnknownUsageTests.A_combined_total_leaves_the_split_unknown`.
- `tokensIn` is uncached input. Cache reads are `tokensCachedIn` and are **not** added into `tokensIn`. Counting them at full weight inflates spend many times over. Pinned by `UsageBillableTests.Cache_reads_are_not_full_price_input` and `UsageBillableTests.Cached_input_may_exceed_uncached_input`.
- Spend uses `InvocationUsage.BillableTokens`: cache reads at 1/10, cache writes (`tokensCacheCreation`) at 5/4, a combined total (codex) as reported. The SQL in `SqliteMessageStore.SpendAsync` must stay on those same integer weights. Pinned by `UsageBillableTests.Cache_writes_bill_at_five_quarters`, `UsageBillableTests.A_combined_total_is_not_reweighted`, and for the SQL by `SpendSqlTests.Cache_reads_are_weighted_as_BillableTokens_weights_them`, `SpendSqlTests.Cache_writes_are_weighted_as_BillableTokens_weights_them` and `SpendSqlTests.A_combined_total_is_counted_as_BillableTokens_counts_it`.
- A run is billed once, however many deliveries it answered. A batched run closes each delivery with its own terminal row; only the first carries the token figures, the rest carry `usageCountedOn` and no figures, and both spend queries skip them. - A trigger's **daily token cap** (`triggers.daily_token_cap`, `auth-010`, NULL for none) counts the measured `BillableTokens` of the runs its fires started since midnight in its timezone (UTC when it has none), plus the Manager runs those runs woke (the terminal rows caused by their `completed`, `failed` or `handback` rows) - `IMessageLog.GetTriggerSpendAsync`, on the same SQL weights as the workflow spend. An unmeasured run is counted as `unmeasuredRuns`, never as zero, and never reaches a cap. A fire once the cap is reached - schedule, event or folder - is skipped: `schedule.skipped` with the reason `daily token cap reached`, the trigger's outcome `capped`, and a `tenant_events` row; it fires again the next day. A clock trigger sleeps until the next day's first occurrence in its timezone (`TriggerCost.ResumeAt`), and `cappedUntil` names that same time, also after a person edits the schedule and re-arms it from now (that fire only skips again). The first capped skip of a day is one unit: its count and sleep, its `schedule.skipped` row and its tenant row commit in one transaction (`IMessageLog.AppendWithinAsync`); when the rows cannot be written nothing is stored and the next fire tries again. Pinned by `CappedTriggerSleepTests.A_first_capped_skip_whose_rows_cannot_be_written_stores_nothing_and_the_next_fire_tries_again`. Pinned by `CappedTriggerSleepTests.A_schedule_capped_on_its_third_run_logs_one_skip_and_sleeps_until_the_next_days_first_occurrence` and `CappedTriggerSleepTests.An_edited_schedule_still_over_its_cap_shows_capped_until_the_next_days_first_occurrence`. Pinned by `TriggerCostControlTests.A_trigger_at_its_cap_skips_its_next_fire_with_the_reason_and_the_tenant_row_and_fires_again_the_next_day`, `TriggerCostControlTests.An_event_trigger_at_its_cap_skips_the_next_event_with_the_reason`, `TriggerCostControlTests.Spent_today_counts_the_manager_runs_its_runs_woke_and_never_counts_an_unmeasured_run_as_zero`, `TriggerCostControlTests.Unmeasured_runs_never_reach_a_cap`, `TriggerCostControlTests.The_day_starts_at_midnight_in_the_triggers_timezone` and `TriggerCostControlTests.A_members_recent_cost_is_the_median_of_its_measured_runs_and_counts_the_unmeasured`.
- A workflow budget reads spend **since the last nudge**, and the wake uses that same figure. Two different figures refuse a dispatch the pump would have allowed. Pinned, for the window and the pump, by `WorkflowBudgetAtTheWakeTests.Spend_since_the_nudge_counts_only_runs_after_it` and `WorkflowBudgetAtTheWakeTests.A_wake_over_the_bound_is_refused_and_a_nudge_lets_the_next_one_run`. ## Solution packages

## Admission

- `wip.maxRunning` (a tenant setting, falling back to `Wip:MaxRunning`) is instance-wide and shared across users. Default `max(2, cgroup CPUs)`, else 4. `0` is unlimited (`WipLedgerTests.Zero_is_unlimited`). The setting and its fallbacks are pinned by `TenantSettingsTests.A_row_wins_over_appsettings_which_wins_over_the_built_in_default`, `TenantSettingsTests.The_default_running_limit_is_the_cpu_count_when_that_is_above_two` and `TenantSettingsTests.The_cgroup_cpu_limit_is_read_from_cpu_max`. The "else 4" arm is not pinned: with no CPU count passed, `TenantSettings` reads the real `/sys/fs/cgroup/cpu.max`, and there is no seam to make it read nothing. The container memory limit does not replace it; that is a statement of intent, not a behaviour. It changes at runtime through `WipLedger.SetMax`, under the ledger's lock; lowering it evicts nothing. Pinned by `WipClaimTests.Raising_the_limit_at_runtime_starts_waiting_work_without_a_release` and `WipClaimTests.Lowering_the_limit_at_runtime_evicts_nothing_and_holds_the_next_start`.
- Work that cannot start is **waiting**, not failed. Nothing is refused, `tell` is never held, and there is no `wait` tool. `GET /api/wip` names who is running and who is waiting, by team and member; `ContainerSnapshot.Held` marks the container, and `/api/teams/rollup` counts both per team. A person blocked by a colleague's run must be able to see that it is a colleague's run. Pinned by `WipLedgerTests.The_cap_holds_work_and_names_who_has_the_slots`, `TellNeverHeldTests.A_tell_into_a_full_pool_answers_at_once_and_the_run_waits_visibly`, `LimitLoweredAcceptanceTests.Lowering_4_to_2_with_six_runnable_members_runs_two_and_queues_four_in_order`, `HeldTeamRollupTests.A_team_whose_manager_waits_for_a_slot_reads_waiting_for_a_slot`, `WipClaimTests.Work_over_the_cap_waits_and_starts_when_the_slot_is_released` and `WipClaimTests.A_held_claim_shows_on_the_snapshot_until_the_run_starts`.
- A paused team takes no slot and holds no place in the queue: its waiting work is passed over for a released slot. Pinned by `WipClaimTests.A_paused_team_is_passed_over_for_a_released_slot`.
- A released slot goes to whoever has waited longest (FIFO). The claim loop waits on `WipLedger.Changed`, never a poll. Pinned by `WipClaimTests.A_released_slot_goes_to_the_longest_waiter` and `WipClaimTests.Released_slots_go_to_waiters_in_the_order_they_queued`.
- A Manager has one reserved slot above the limit, so a pool full of members never starves the Manager that would free them. Pinned by `WipClaimTests.A_manager_is_not_held_behind_its_workers`, `WipClaimTests.A_pool_full_of_members_still_starts_a_manager_wake` and `WipClaimTests.A_manager_uses_one_reserved_slot_and_no_more`.

## Settings

- Instance-wide settings are `tenant_settings` rows over `appsettings.json` over built-in defaults, read once at start and held by `TenantSettings`. A consumer is handed a delegate, never a number: a value captured in a constructor brings the restart back. Every write appends a `tenant_events` row, in the same transaction. Pinned by `TenantSettingsTests.A_write_applies_without_a_restart_and_appends_an_audit_row` (a write takes effect without a restart, for `wip.maxRunning` and the workflow budget, and appends the audit row), `TenantSettingsTests.A_value_is_not_written_when_its_audit_row_cannot_be`, `TenantSettingsTests.A_row_wins_over_appsettings_which_wins_over_the_built_in_default` and `TenantSettingsTests.An_invalid_value_is_refused_naming_the_field_and_nothing_is_written`. "A delegate, never a number" is not pinned as a rule over every consumer: whether a constructor captured a value is visible only by exercising each consumer after a write, and only the two above are exercised.

- A person's settings write outside `tenant_settings` appends its `tenant_events` row in the same transaction too, and does not happen when that row cannot be written (the store takes a `TriggerAudit`, never the swallowing `TenantLogging.WriteAsync` after the save): a trigger's create, change and delete, a member's plugin settings, a member edit (`member.changed` and `member.instructions-changed`), and a team's workflow budget, additional instructions, member agents, pause and resume and a repository's default branch, and the Concierge agent. Pinned by `SettingsAuditTransactionTests` (every case, among them `A_team_is_not_paused_or_resumed_when_its_tenant_row_cannot_be_written`) and `TriggerAuditTransactionTests.A_change_is_not_saved_when_its_tenant_row_cannot_be`. The Agent catalog (`PUT /api/agents`) lives in `agents.json`, which cannot share that transaction, so its `agents.saved` row is written FIRST, unswallowed, and neither the file nor the live catalog changes when it cannot be, as the documents delete does. Pinned by `SettingsAuditTransactionTests.The_agent_catalog_is_not_saved_when_its_tenant_row_cannot_be_written`. Not in this shape, so not pinned: a repository's contributor settings (their row records whether the clone was brought in line, which is known only after the save), and a team's environment and repository list (no tenant row at all).

- "System packages" (`system.packages`) is the one setting that applies at the next START, not at once: the entrypoint installs it with `apt-get` as root before the host runs, so the host copies the list to `<dataRoot>/system-packages` at start and on every change, and the entrypoint reads that file, never the database. A name is checked against the same pattern twice, by `SystemPackages.IsValidName` and by `scripts/prepare-volume.sh`, because the file reaches a root shell; a failed install is logged and the host starts anyway. Pinned by `SystemPackagesSettingTests.A_change_is_written_to_the_file_the_entrypoint_reads`, `SystemPackagesSettingTests.A_name_that_is_not_a_package_name_is_refused_and_nothing_is_written`, `SystemPackagesSettingTests.The_list_survives_a_restart_and_the_file_is_rewritten_from_it`, `PrepareVolumeTests.Only_valid_package_names_reach_apt_get_and_nothing_else_is_run` and `PrepareVolumeTests.A_failed_install_is_logged_and_the_entrypoint_starts_the_host_anyway`.

## Users on the volume

- Two users, fixed ids: `harness` 10001:10001 runs the host and is also in group `agent`; `agent` 10002:10002 runs agent children and the Concierge PTY (the host finds it by name). The entrypoint starts as root, sets ownership on every start (`scripts/prepare-volume.sh ownership`: host files `messages.db*`, `keys`, `agents.json*`, `agent-launch.json*` (what `--doctor` reports as agentLaunch), `logs`, `backups`, `host.lock*`, `system-packages*` and `connections` (the operator CLI's `connect` exchange, which carries authorization codes) are harness-only 600/700; everything else, and any `FileBrowser__Roots__<n>__Path` outside the volume that, resolved with `realpath -e`, is not a system directory (`/var/*` included), is agent's with directories `g+rwxs` and files `g+rw`; inside `agent-home` only the owner changes, except that the home itself and `.grok` (directory `g+rwxs`, files directly in it `g+rw`) are the group's so the host can rewrite grok's `config.toml`; the Claude login, `.ssh` and the rest keep their modes, because ssh refuses a group-readable key), sets `safe.directory '*'` and the GitHub credential helper in the SYSTEM git config (root never writes into the shared HOME) and `/tmp` 1777, then drops to `harness` with `umask 0007` (not 0002: files the host creates in the 0750 data root between starts must not be readable by agent) and setpriv keeping only CAP_SETUID, CAP_SETGID and CAP_KILL in the ambient and bounding sets. KILL is there because a process of another user refuses the host's signal without it: a watchdog or Stop could not end an agent. The data root is harness:agent 0750, so `agent` cannot create a top-level entry: one it needs is made by the entrypoint first. Root finds commands in the system folders only (the entrypoint's first command and prepare-volume.sh set that PATH), and the host's PATH, like the image's ENV, puts the system folders before every agent-writable tool folder (`/data/bin`, `npm-global/bin`, ...): otherwise a `find` or `git` an agent plants there runs as root or as the host; setpriv and dotnet are called by absolute path. Root also reads no user config from `agent-home`, which agent owns: both scripts set `HOME=/root`, `GIT_CONFIG_GLOBAL=/dev/null` and `PYTHONNOUSERSITE=1` and unset the XDG folders before their first command, because root's git would read agent's `.gitconfig` (a malformed one stops the boot) and python3 in an apt maintainer script would import agent's `usercustomize.py` as root; only the CLI install and the host exec get `HOME=/data/agent-home` back, on their own lines. The image's `ENV HOME` stays agent-home for `podman exec` logins and `--doctor`. Pinned by `PrepareVolumeTests.Root_runs_on_system_folders_only`, `PrepareVolumeTests.Root_reads_no_gitconfig_or_python_user_site_from_the_agents_home`, `PrepareVolumeTests.A_command_planted_on_the_callers_path_is_not_run`, `PrepareVolumeTests.An_all_root_volume_gets_the_host_files_for_harness_and_everything_else_for_agent`, `PrepareVolumeTests.A_second_start_changes_nothing`, `PrepareVolumeTests.A_file_browser_root_outside_the_volume_is_agents_and_a_system_directory_is_refused`, `PrepareVolumeTests.The_entrypoint_sets_ownership_and_installs_packages_as_root_then_drops_to_harness`, `PrepareVolumeTests.The_host_keeps_only_setuid_setgid_and_kill_and_its_agent_children_keep_nothing` (runs the exec line for real when the suite is root), `PrepareVolumeTests.Nothing_but_chmod_1777_touches_tmp`, `PrepareVolumeTests.A_script_run_by_these_tests_sees_only_the_environment_it_is_given` (a runner's `FileBrowser__Roots__*` never reaches a real chown) and `PrepareVolumeTests.The_image_carries_both_users_at_fixed_ids_and_the_tools_to_switch`. Every tarball the image unpacks into a system folder is unpacked `--no-same-owner`: otherwise the Node tarball keeps its uid 1001, and `/usr/local/bin`, `node` and `npm` belong to a user the image does not have. Pinned by `PrepareVolumeTests.Every_tarball_the_image_unpacks_is_owned_by_root`. That the users exist in a built image is not pinned: neither suite builds the image.

## Files

- File-browser roots are container paths. The data root is always included. Listing a root means a team may be placed there. Do not list a path you would not let agents write under. "The data root is always included" is pinned by `FileBrowserRootsTests.With_nothing_configured_the_data_root_is_listed` and `FileBrowserRootsTests.A_configured_root_adds_to_the_data_root_and_does_not_replace_it`. The rest is guidance on what to configure, not behaviour, so it is not pinned.
- Inside the container, "another drive" is another mount. Add it to `FileBrowser:Roots` and to the `podman run` command. The setting is not a host path. Not pinnable: this is about how the container is deployed, which neither test suite runs.

## Tests

- A test that was not seen to fail for the right reason does not prove the fix.
- A mock in the wrong shape is a confident test. Thirteen green cases while the feature 404s is the failure mode.
- These two are rules for writing tests, so no test can pin them.
- A test Host never starts a real agent. The release runs the suite inside the product image, where the agent CLIs are installed and signed in, and a test that fires a trigger or tells a member would otherwise start a real, paid run with the signed-in account's tools, which outlives its test Host. `AgentCliIsolation` puts a stub of every built-in language-model preset's command (not `bash` or `cat`, which call no model) first on the test process's PATH at load; the stub says why and exits 1. A test that wants a real program names its own command. Pinned by `AgentCliIsolationTests.Every_built_in_presets_command_resolves_to_the_stub_for_this_test_process` and `AgentCliIsolationTests.The_stub_says_why_and_fails_without_starting_anything`.
- `dotnet test` on this repo's Microsoft.Testing.Platform projects can report "zero tests" even when the assembly has tests. Run the test dll directly: `dotnet tests/Harness.Tests/bin/Debug/net10.0/Harness.Tests.dll` after a build. This describes the tooling, so it is not pinned.
- A rule above that names no test has none. A rule marked **Currently VIOLATED** is pinned by a Skipped test that fails when un-skipped; the fix removes the Skip. A rule that cannot be pinned says so, and why.
